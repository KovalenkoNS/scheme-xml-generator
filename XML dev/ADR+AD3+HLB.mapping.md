# Сопоставление `ADR+AD3+HLB`: библиотека → графический XML

## Итог

В `Library AD3_v2.xml` найден не предполагаемый, а явный библиотечный шаблон `TEMPLATE ID="19963" Name="ADR+AD3+HLB"`. Его содержимое однозначно материализовано в `ADR without input.xml`:

| Библиотека | Количество | Графический экспорт | Количество |
|---|---:|---|---:|
| `grprim` типов 31/34/36/37 | 34 | `ISAGraf/Blocks/Block` | 34 |
| `grprim` типа 20 | 27 | `ISAGraf/Links/Link` | 27 |
| `grprim` типов 1/2/7 | 8 | `GrObj/OnePrim` | 8 |
| **Всего** | **69** | **Всего** | **69** |

Совпали все 34 блока, все 27 трасс линий и все 54 ссылки на их концы. Это полное соответствие 1:1.

## Где расположен библиотечный шаблон

```xpath
/root/SECTION[@Num='2']/OTHER/OBJTYPE[@ID='2035']/CHILD/
OBJTYPE[@ID='2251' and @Name='AD3_v2']/TEMPLATES/
TEMPLATE[@ID='19963' and @Name='ADR+AD3+HLB']
```

В исходном файле это строки 76302–78502. Метаданные шаблона:

```text
DISC     = Обработка дублированных аналогов
DPARAMS  = 2
WIDTH    = 1400
HEIGHT   = 960
FONCOLOR = 15461355
```

Эти размеры и фон описывают библиотечный шаблон, но не заменяют параметры страницы `OnePOU`: шаблон вставляется в уже существующую страницу.

## Геометрическое преобразование

Точка вставки в исследованном экспорте:

```text
DX = 300
DY = 100
```

Для всех 34 блоков:

```text
Xout = Xtemplate + DX
Yout = Ytemplate + DY
WIDTHout  = WIDTHtemplate
HEIGHTout = HEIGHTtemplate
```

Для всех 27 связей та же операция применяется к каждой точке `[PL]`.

Семь из восьми `OnePrim` используют ту же формулу. Для единственной полилинии `OBJTYPE=7` правильно смещается список точек `[PL]`, однако атрибуты `X/Y/HEIGHT` exporter пересчитывает иначе. Для неё авторитетной геометрией следует считать `[PL]`.

## Правила преобразования примитивов

### Блоки

`GROBJTYPE` 31, 34, 36 и 37 становятся `ISAGraf/Blocks/Block`.

| Поле библиотеки | Поле результата |
|---|---|
| `GROBJTYPE` | `Block/@GROBJTYPE` |
| новый ID вместо `grprim/ID` | `Block/@T11ID` |
| `X/Y/WIDTH/HEIGHT` | `Graphics/@X,Y,WIDTH,HEIGHT` с offset |
| `[TEXT]` | `Params/@T11Text` |
| `[CI]`, `[CO]` | `Params/@CI`, `Params/@CO` |
| `[VMODE]` | `Params/@VMODE`; при отсутствии — `0` |
| `[COMMENT]` | `Params/@Commented` в нижнем регистре |
| `OBJMSID` | `Params/@IsaObjId` |
| `CARDID` | `Params/@cardId` через таблицу remap |
| значение карточки проекта | дочерний `IV` |

`[Order]`, `PAGEID`, `MSORT`, `FIELDSID`, `GROUPID`, `LAYERNUM`, `TEMPLATEGROBJID` и `EXPARAMS` в объектный XML не переходят.

Правило для `Block/@Info`:

```text
card-bound field:  actualCard.Info + [TEXT]     // TAG + ".IN0"
card-bound object: actualCard.Info              // TAG + "_ADR"
CARDID=0, TYPENAME задан: TYPENAME              // PACK8
иначе: [TEXT]                                   // FALSE
```

Единственное расхождение параметров среди всех 34 блоков: библиотечный шаблон 19963 хранит для `AD3_HLB` `CO=15`, а экспорт содержит актуальное `CO=17`. Соседний более новый шаблон 19962 также использует `CO=17`, поэтому сигнатуру блока нужно разрешать по актуальному типу, а не слепо копировать из старого шаблона.

### Связи

`GROBJTYPE=20` становится `ISAGraf/Links/Link`.

| Поле библиотеки | Поле результата |
|---|---|
| `[PL]` | `PointList/@PL`, все точки с offset |
| `[FP]` | `FirstPoint/@FP`, старый ID заменён новым `T11ID` |
| `[LP]` | `LastPoint/@LP`, старый ID заменён новым `T11ID` |
| `[BN]` | `Link/@GetBitNum` |
| `[CT]` | `Link/@ConvertTo` |
| `PENCOLOR` | `Link/@Color` |
| `DRAWTYPE=1` | `Link/@UserEdit="true"` |

Значения направления `0/-1` нормализуются как `False/True`. Endpoint rectangle `0,0,0,0` в четырёх новых связях нормализован exporter'ом до `0,0,100,20`.

### Оформительские объекты

`GROBJTYPE` 1, 2 и 7 становятся `GrObj/OnePrim`:

```text
ID          → SourceT11ID (новый)
GROBJTYPE   → OBJTYPE
PENPARAMS   → PenParams
PENCOLOR    → PenColor
BRUSHCOLOR  → BrushColor
GRADCOLOR   → GradColor
NAME        → ScriptName
PARAMS      → PARAMS
```

## Карточки экземпляра

Шаблон ссылается только на 7 из 20 деклараций `ISAOBJLIST`. Все повторные обращения `.IN0`, `.IN100`, `.Out` и т. п. получают отдельные `T11ID`, но используют одну основную карточку AD3.

| Library `CARDID` | Prefix | Тип | `cardId` в образце |
|---:|---|---|---:|
| 507254 | пустой | AD3_v2 | 706662 |
| 552226 | `_ADR` | ADR_v3 | 706663 |
| 556599 | `_HLB` | AD3_HLB | 706664 |
| 507255 | `_MOS` | BOOL | 706665 |
| 544835 | `_SP_HH` | REAL | 706666 |
| 544836 | `_SP_LL` | REAL | 706667 |
| 556601 | `_SRV` | BOOL | 706668 |

Для базового имени `TAG` создаются:

```text
TAG
TAG_ADR
TAG_HLB
TAG_MOS
TAG_SP_HH
TAG_SP_LL
TAG_SRV
```

Старые `CARDID` — ссылки на декларации внутри библиотеки. Их нельзя переносить в проект как реальные `cardId`.

`ISAOBJ/INITIALVALUE` в библиотеке содержит значения, которые нужны для `<IV>`: составные значения AD3_v2 и ADR_v3, `FALSE` для MOS/SRV и `0.0` для SP_HH/SP_LL. У AD3_HLB значение пустое и материализуется как пустой `<IV/>`. Составной `IV` основной AD3 повторяется у всех обращений `TAG.member`. Таким образом, для данного формата `IV` можно получить непосредственно из ближайшего `ISAOBJLIST`; project-specific остаются новые `cardId`, описания и `KLPath`.

## Топология

```text
ADR.Out  → REAL_TO_DINT.X → AD3.Xin
ADR.Stat → INT0.X → ANY_TO_DINT.Input → AD3.Xs

AD3.IN0, IN100, Av, PAv, Pv, Pn, PAn, An,
NSporog, Out и TAG_MOS → соответствующие входы HLB

TAG_SRV → AD3.Kno_sig
8 × FALSE → PACK8.IN0..IN7
```

У `ADR_v3` нет ни одной входящей связи. Поэтому имеющийся файл действительно представляет вариант «without input»; внешние сигналы должны добавляться отдельными блоками и `Link`, направленными на входные порты ADR.

## Алгоритм материализации

1. Найти `TEMPLATE[@ID='19963']/CONTENTS`.
2. Получить контекст целевой страницы `Common` и `OnePOU`.
3. Создать 7 карточек и словарь `old CARDID → new cardId`.
4. Выделить новые уникальные `T11ID` и построить `old grprim ID → new T11ID`.
5. Первым проходом создать 34 `Block`.
6. Вторым проходом создать 27 `Link`, переписав оба endpoint через ID-map.
7. Создать 8 `OnePrim` и применить offset к геометрии.
8. Сформировать `ISAOBJSINFO` из уникальных положительных `OBJMSID`.
9. Сформировать `ISACARDSINFO` из 7 созданных карточек.
10. Добавить реально используемые определения шрифтов.

В образце блоки занимают `T11ID` 2172418–2172451, затем наблюдается разрыв ровно на 27 ID связей, а `OnePrim` занимают 2172479–2172486. Для генератора существенно не конкретное начало диапазона, а уникальность ID и согласованная замена всех ссылок.

## Параметризованный прототип

Файл `ADR+AD3+HLB.graphic.template.xml` содержит полный графический XML с 34 блоками, 27 связями и 8 примитивами. Он является корректным UTF-8 XML, но до подстановки значений не предназначен для импорта.

Основные группы placeholder'ов:

- `{{PROJECT_*}}`, `{{CONTROLLER_*}}`, `{{POU_*}}`, `{{PAGE_*}}` — контекст страницы;
- `{{TAG}}`, `{{DISPLAY_NAME}}`, `{{KL_PATH}}` — экземпляр объекта;
- `{{CARD_*}}` — новые project-specific card ID;
- `{{ID_*}}` — новые уникальные T11ID; endpoints уже используют те же имена;
- `{{IV_*}}` — значения созданных карточек.

Координаты прототипа соответствуют точке вставки `(300,100)`. Для другого размещения нужно прибавить дополнительный offset ко всем `Graphics X/Y`, точкам `PointList/PL` и геометрии `OnePrim`; у `OBJTYPE=7` следует ориентироваться на `[PL]`.

## Ограничения исходного экспорта

`ADR without input.xml` формально не является корректным XML 1.0/UTF-8:

- в семи `KLPath` находятся по два сырых байта `0x08`, всего 14;
- `LibName="Системная"` и `LibName="Пользовательская"` записаны байтами CP1251 при общей декларации UTF-8.

Строгий XML parser падает без предварительной санации. Параметризованный прототип нормализован в UTF-8 и использует `{{KL_PATH}}`; если целевой импортёр требует проприетарные разделители, их следует добавлять только на финальном этапе сериализации.

Файл `ADR with input.xml`, показанный как вкладка IDE, физически отсутствует в каталоге, поэтому отдельный diff варианта с подключённым входом выполнить нельзя.
