## Действующая граница после пакета 003

С 29.09.2026 FBD доступен только через библиотечные `/api/generate` и `/api/generate/library-do`. Прежние встроенные AO/AI/DI/DO/native850 FBD возвращают HTTP `410`; библиотека не заменяется скрытым встроенным профилем. NOT — отдельный флаг инверсии выбранного DO-сигнала, не выбор шаблона и не обязательный признак ПАЗ. Канонический ST API назначений — `/api/mappings/generate`; `/api/skz/generate` сохраняется как исторический адрес того же обработчика.

Ограничения подтверждённых рабочих профилей: модульный DO FBD с диагностикой — CPU850 и `measurement-quality`; AO ST — CPU715; DI ST — CPU850 и `measurement-quality`; полная HMI-диагностика — CPU715. AI/DO ST используют поддержанные профили адресации. Эти ограничения реализации не определяют состав ПЛК всех областей. Текущие страницы и API: [глава 02](02-current-implementation.md); фактические проверки: [verification пакета 003](../specs/003-unified-workspace/verification.md).

## Почему CPU — не адресация

Нативные `XML dev/AI_GRAF.xml` и `DO_GRAF.xml` объявляют CPU715 и используют `ValueDINT/Status/Value`. При этом `XML dev/Group_AI_w_physic.xml` объявляет CPU850 и тоже использует `_IO_IU…ValueDINT/Status`. Профиль СКЗ850 использует другую модель каналов — `Measurement/Quality`. Следовательно, одно имя CPU не описывает драйвер, аппаратную конфигурацию или версию библиотеки.

В библиотечном режиме физический граф остаётся IU/QU. В СКЗ ST профиль выбирается отдельно. Автоматическое значение — удобный default конкретного режима, а не универсальное соответствие CPU и драйвера. Пользователь сверяет выбранный профиль и числовые ModuleID с целевым проектом.

| Профиль СКЗ ST | AI: чтение значения / статуса | DO: запись выхода D32V |
|---|---|---|
| `legacy-iu-qu` | `tag.Xin := _IO_IU<ID>_<ch>.ValueDINT;` / `tag.Xs := _IO_IU<ID>_<ch>.Status;` | `_IO_QU<ID>_<ch>.Value := module._NN;` |
| `measurement-quality` | `tag.Xin := _IO_I<ID>_AI16H_<ch>_VAL.Measurement;` / `tag.Xs := QUAL_STAT(_IO_I<ID>_AI16H_<ch>_VAL.Quality);` | `_IO_Q<ID>_DO32P_<ch>_VAL.Measurement := module._NN;` |

Для ST AI/DO CPU715 допускается только legacy: образца его Measurement/Quality нет. Для AI/DO CPU850 доступны оба явных профиля. Это параметризация физической модели; исполнение legacy ST на конкретном контроллере ещё не подтверждено. AI Measurement/Quality требует `QUAL_STAT`.

В обоих DO-профилях ST всегда назначает все 32 физических выхода каждого модуля через D32V._00…_31, в том числе свободные позиции без технологического тега Excel. FBD не дополняется вымышленными BOOL; AI сохраняет прежнее правило перечисленных каналов. Основание: [TASK-0009](tasks/TASK-0009-do-st-full-channels.md).

DI ST доступен только для CPU850 Measurement/Quality. На каждый модуль он назначает `module.iNN := _IO_I<ID>_DI32_<ch>_VAL.Measurement;` для всех 32 каналов и `module.Stat := ANY_TO_DWORD(QUAL_STAT(_IO_I<ID>_DI32_0_VAL.Quality));` один раз. Требуются `QUAL_STAT` и `ANY_TO_DWORD`. Разреженные FBD-получатели и SPARE не сокращают физические DI-присваивания. DI legacy и DI ST715 отклоняются UI и генератором; детали и границы нативного свидетельства — в [главе09](09-di850-native-semantics.md).

## Контракты API и интерфейс

Основной `/api/generate` принимает опциональный контекст для legacy-запроса и `pous`:

```json
{"context":{"controllerTypeName":"TENIX-CPU850"}}
```

Это дополнение к полям схемы, не самостоятельный запрос генерации. Контекст действует на весь XML и не изменяет `config.json`. Если он отсутствует или равен `null`, сохраняется прежний default конфигурации. Явный объект контекста требует полного допустимого имени CPU; `{}` и неизвестная модель отклоняются. Остальные параметры импорта остаются из конфигурации/полей POU.

AO TXT и СКЗ используют `context.controllerTypeName`. Типы ограничены `TENIX-CPU715` и `TENIX-CPU850`; запросы AO FBD/ST850 дополнительно отклоняются как неприменимые к целевой ПАЗ. В СКЗ ST AI/DO дополнительно принимается `context.physicalProfile`: пустой/отсутствующий → legacy для715, Measurement/Quality для850; либо одно из двух точных имён профиля. В обычном FBD физический профиль не применяется. Исключение — новый DO ПАЗ `native850`: только CPU850 + Measurement/Quality, явные ModuleID для диагностических карточек. Интерфейс сохраняет ручные выборы при переключении режимов и не заменяет выбранный CPU нативным default при поздней загрузке профиля.

`GET /api/skz/profile` дополнительно публикует `controllerTypes`, `physicalProfiles`, `defaultPhysicalProfiles`. Служебные ControllerID/ResourceID/GroupID/POUNum из примеров не становятся универсальными при переключении CPU; их необходимо сверять с назначением.

`POST /api/skz/preview` и `/api/skz/generate` принимают подготовленные карты AI/DO и исходный IO XLSX для DI/DO. Исходный DO использует Tag No + `_DDVH`, поля Main_module/Main_module2/Redundant_module/Redundant_module2 и общий Channel; Loop не подменяет имя. DI сохраняет Main/Redundant → C1/C2. SCS определяет ПЛК; остальные направления исходной книги пропускаются с предупреждением. Подготовленные AI/DO-файлы сохраняют прежние буквальные имена из выражений. Пользователь выбирает DO, DI либо их совместный состав, количество модулей и ModuleID; форматы multipart/context/config не меняются, результат разделяется по ПЛК. При совместном ST с DI обязателен профиль CPU850 Measurement/Quality; только DO сохраняет прежний выбор CPU/профиля.

DI-default: CPU850, `ControllerID=189312`, `ResuorceID=644`, `GroupID=19814`, первый `POUNum=23` в ST / `25` в FBD. Они перенесены из одной нативной POU: для четырёх групп B01 получаются пересекающиеся ST23…26 и FBD25…28. При совместном импорте задаются свободные непересекающиеся диапазоны. Структурная проверка каждого XML по отдельности не проверяет совместный импорт в SCADA.

Смешанный DO/DI-выбор использует один общий явно выбранный контекст, а не разные Common для направлений одного XML. Без context API берёт default первого выбранного направления в отсортированном плане, обычно DI. Пользователь сверяет все служебные ID и POUNum; принадлежность SCS не выводится из этих нативных чисел.

Книга, явно выбранная владельцем, находится в соседнем `../XML dev`, а не в `output/`. В ней 619 DI-строк, из которых одна SPARE; итог — 50 модулей, 1236 получателей C1/C2, 8 POU и 3 ПЛК. Пустота BL:BP не блокирует исходный профиль после подтверждения правил владельцем. Q-XML-007 закрыт по данным и правилам входа; полная спецификация — [глава09](09-di850-native-semantics.md).

TASK-0007 добавляет 487 DO-строк из того же файла: четыре разных размещения в каждой дают 1948 назначений, 72 модуля и 12 групп. Совместный состав DI/DO — 20 групп, 122 модуля, 3184 подключения в трёх ПЛК. Правило имён и контрольные размеры выходов приведены в [разделе10.2](04-xml-formats.md#102-do-из-исходного-io-xlsx-с-сохранением-di); факт прохождения проверок фиксируется в TASK-0007. HMI850, AO850 и набор допустимых аппаратных профилей не расширяются.

## Оставшаяся работа

- DI850: проверить импорт, диапазоны POUNum, порядок выполнения ST/FBD, физические ModuleID и C1/C2 в целевой SCADA. Исходная книга и правила преобразования получены; [Q-XML-007](04-xml-formats.md#q-xml-007--новые-профили-скз-aodi) закрыт по входному формату. AO850 исключён из ожидания.
- Прямая физическая DI/DO FBD-привязка850 в основном рабочем пространстве не подтверждена новыми DI XML: они используют отдельный ST. Не снимать ограничение этого режима по факту появления программного DI FBD.
- CPU850 полная диагностика: нужны CPU-символ, компоновка и рецепторы — [Q-HMI-002](05-operator-interface-and-xls.md#q-hmi-002).
- Legacy ST715/850 получен по связям FBD, а не перенесён из отдельного ST-экспорта; необходим протокол импорта, компиляции и проверки адресов на целевой конфигурации.
- XLS остаётся выгрузкой объектов известных типов модулей/резервов, без CPU-объектов и без заявления о прямом импорте XLS в SCADA.

Результаты автоматических проверок и сборки фиксируются в карточке задачи, не заменяя протокол SCADA.
