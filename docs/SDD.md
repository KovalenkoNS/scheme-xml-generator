# Единый SDD: GitHub Spec Kit в VS Code

[Обязательные правила SDD](../.specify/memory/rules.md) читаются перед каждым изменением. Все решения владельца являются инструкциями, а нарушение применимого правила — ошибкой FAIL. В plan.md и verification.md указывать применимые ID и фактические доказательства. До устранения нарушения нельзя завершать работу или ставить verified. CODE-001/CODE-001-T проверяются по реальному размещению исходников и тестов; CODE-002 — по содержанию комментариев функций, а не наличию формальной строки.

Формат принят владельцем 28.09.2026 для Host-client, Host-server, Host-database и XML Generator. Используется GitHub Spec Kit **1.0.12**, интеграция **Codex**, скрипты **PowerShell**. Каждый репозиторий хранит собственные спецификации, принципы и результаты проверок.

Обновление фактического соединения с оркестратором: [006-live-host-session](../specs/006-live-host-session/spec.md), [контракт](integration/host-session.md). Уточнение владельца от 30.09.2026: обновлять соединение; не расширять запрос до таблиц/IO-данных или версий приложений.

## Границы проектов

| Проект | Ответственность |
|---|---|
| Host-client | Поставляемый оркестратор всех доступных приложений и обмена данными между модулями и сервером |
| Host-server | Авторизация клиентов; хранение и маршрутизация IO-листов проекта SCADA; серверный доступ к PostgreSQL |
| Host-database | Инфраструктура PostgreSQL, схема и миграции |
| XML Generator | Независимое ПО генерации XML-файлов SCADA |

Изменение межпроектного контракта описывается в затронутых репозиториях с явными ссылками на связанные спецификации. Независимость XML Generator сохраняется; наличие описанной целевой интеграции не означает, что она реализована. Детальные правила проекта: [constitution.md](../.specify/memory/constitution.md), [AGENTS.md](../AGENTS.md).

## Один формат

Уточнения предметного контекста от 29.09.2026: [ADR-0010](decisions/ADR-0010-host-context-and-plc-domains.md), [круги Эйлера](11-project-domains.md), пакет [002-context-clarification](../specs/002-context-clarification/spec.md). Host ведёт раздельные контексты приложения и рабочего проекта; серверные IO-листы — только структурированные записи БД, модулям в первой версии доступно только получение. Это требования, не утверждение о реализованной интеграции.

При противоречии запроса действующим правилам или контексту агент сообщает конкретное расхождение со ссылкой на документ и просит уточнение. До ответа приостанавливается только зависимая часть; независимая разрешённая работа продолжается. Ответ и изменение решения записываются в контекст, [правило работы](07-workflow-and-decisions.md).

```text
.specify/memory/constitution.md       принципы конкретного проекта
.specify/templates/                  одинаковые базовые шаблоны Spec Kit
.specify/scripts/powershell/          официальные скрипты
.agents/skills/speckit-*/SKILL.md      команды Codex
specs/NNN-short-name/
  spec.md                            что требуется и критерии приёмки
  plan.md                            решение, ограничения, этапы и проверки
  tasks.md                           последовательные задачи T001, T002, ...
  verification.md                    фактические результаты по FR-001, ...
```

`research.md`, `data-model.md`, `contracts/`, `quickstart.md` и `checklists/` добавляются, когда этого требует изменение. `verification.md` — единое локальное дополнение к Spec Kit, а не обязательный файл upstream. Шаблон: [verification-template.md](../.specify/templates/verification-template.md).

Продуктовые справочники, текущие контракты и ADR остаются по существующим адресам. Исторические `docs/tasks/`, `specs/changes/`, `.kiro/specs/` не переписываются и не используются для новых пакетов. Для продолжения старой задачи создаётся один новый пакет со ссылкой на историю и перечнем оставшихся работ.

## Работа в VS Code

1. Открыть **корень нужного репозитория** в VS Code. Для общей навигации есть `Develop/scada-sdd.code-workspace`; перед работой выбрать нужную папку и вести Codex в её контексте.
2. В установленном расширении Codex ввести `$` и выбрать навык. Если новые навыки ещё не видны, перезапустить сеанс Codex или выполнить `Developer: Reload Window`.
3. Использовать последовательность `$speckit-specify` → `$speckit-plan` → `$speckit-tasks` → `$speckit-analyze` → `$speckit-implement` → `$speckit-converge`. `$speckit-clarify` помогает разобрать существенные неизвестные, `$speckit-checklist` — проверить качество требований. `$speckit-constitution` меняет принципы проекта только в рамках запроса.
4. После реализации заполнить `verification.md`, обновить затронутую документацию текущего поведения и запустить `Terminal: Run Task` → `SDD: check`.

Это команды чата Codex, а не терминала. Отдельное расширение Spec Kit для VS Code не требуется. Навыки доступны в `.agents/skills`; [официальная документация Codex](https://learn.chatgpt.com/docs/build-skills) описывает их обнаружение и вызов через `$`.

## Терминал и задачи редактора

Все команды выполняются из корня выбранного репозитория. Нужны Node.js и Windows PowerShell (либо `pwsh` для переноса оболочки на другую ОС).

```powershell
node scripts/sdd.cjs new client-routing "Маршрутизация запросов клиентов"
node scripts/sdd.cjs check
powershell -NoProfile -ExecutionPolicy Bypass -File .specify/scripts/powershell/check-prerequisites.ps1 -Json -RequireSpec -RequireTasks -IncludeTasks
```

Задача **SDD: new specification** запрашивает slug и название и вызывает официальный `create-new-feature.ps1`. Она создаёт `spec.md`; остальные документы заполняются на соответствующих этапах. Задача **SDD: prerequisites** проверяет наличие документов активной спецификации. **SDD: check** проверяет все новые пакеты и интеграцию.

Активная спецификация хранится локально в `.specify/feature.json`. Для выбора существующего пакета в текущем терминале:

```powershell
$env:SPECIFY_FEATURE_DIRECTORY = 'specs/001-unified-sdd'
```

Переменная имеет приоритет над локальным состоянием. Смена Git-ветки не переключает спецификацию. При переходе к другой задаче удалить переменную (`Remove-Item Env:SPECIFY_FEATURE_DIRECTORY`) либо задать новый путь. Git-расширение Spec Kit здесь не включено: создание спецификации не создаёт коммит и не меняет ветку.

## Требования, задачи, приёмка

В `spec.md` используются истории US1, US2, функциональные требования `- **FR-001**: ...`, наблюдаемые сценарии приёмки и критерии успеха SC-001. В `tasks.md` каждая задача имеет форму `- [ ] T001 [US1] Действие и путь файла (FR-001)`; несколько FR можно перечислить в той же строке. Проверка должна подтверждать требование или значимый риск, а не повторять реализацию.

В `verification.md` указываются дата, среда, команда/шаги, результат, ограничения и таблица:

| Requirement | Check | Result | Evidence |
|---|---|---|---|
| FR-001 | Команда или ручной сценарий | NOT-RUN | Причина отсутствия результата |

Допустимые результаты: `PASS`, `FAIL`, `NOT-RUN`. Статус в `spec.md` (`Status: draft` или стандартная строка Spec Kit `**Status**: Draft`) принимает значения `draft`, `ready`, `implemented`, `verified`, `superseded`.

- `draft`: требования уточняются; план и задачи могут ещё отсутствовать.
- `ready`: требования, план, задачи и матрица проверки заполнены; исполнение входит в запрос.
- `implemented`: работа выполнена, приёмка может быть незавершённой.
- `verified`: задачи завершены, все FR имеют PASS с доказательством.
- `superseded`: пакет заменён; причина и ссылка на преемника сохраняются.

Прямой запрос пользователя разрешает работу в своём объёме. SDD не добавляет повторное согласование каждого файла. При изменении объёма сначала обновляются спецификация и план. Существенные неизвестные фиксируются явно; независимые разрешённые работы продолжаются. Малые правки без изменения контракта можно описать в существующем пакете или описании изменения со ссылкой на требование и проверку.

`SDD: check` проверяет структуру, выбранную версию интеграции, ссылки в новых пакетах/основных инструкциях, FR → задачи → записи результата. Он не исполняет продуктовые тесты, не оценивает истинность PASS, не проверяет сетевые ссылки, Markdown-якоря и все исторические справочники. Для `ready` и позднее нужны все четыре документа. Только наличие документов или успешный `analyze`/`converge` не заменяет фактическую проверку поведения. Импорт и выполнение XML в SCADA требуют отдельного подтверждения в целевой SCADA.

## Версия и обновление

Установленные скрипты и навыки работают из репозитория. CLI нужен для обслуживания установки; на этой машине он находится в `Develop/.toolchains/spec-kit-1.0.12/Scripts/specify.exe`. Исходники: tag `v1.0.12`, commit `e77daa9021d20db26b878f7dfa5640fe5a42d04e`. Происхождение записано в [.specify/upstream.json](../.specify/upstream.json).

Обновление версии оформляется отдельным SDD-изменением для всех проектов: сначала проверка в изолированной папке, затем сравнение шаблонов/навыков и перенос с сохранением constitution и истории. Не запускать принудительную повторную инициализацию поверх рабочих документов. Локальный `verification-template.md` и адаптер `scripts/sdd.cjs` поддерживаются проектом.

В `common.ps1` добавлена одинаковая локальная поправка: UTF-8 для консольного вывода. Без неё Windows PowerShell 5.1 в этой среде заменяет стрелки из шаблона задач управляющим байтом `0x1A`, и JSON `setup-tasks.ps1` становится некорректным. Поправка указана в `upstream.json`; при обновлении её нужно сверить с upstream. Проверка инструмента: `node --test tests/sdd/sdd.test.cjs` (изолированные каталоги, создание спецификации, подготовка плана/задач, JSON, сохранность файлов/ветки и отрицательные проверки приёмки).
