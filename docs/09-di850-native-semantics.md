# 09. DI ПАЗ на ПЛК 850: семантика нативных FBD и ST

Редакция: 28.09.2026. Источники — файлы владельца `DI_850_FBD.xml`, `DI_850_ST.xml`, книга `../XML dev/PS_IO_LIST_SCS_v4_new.xlsx` относительно корня проекта, библиотека DDR и подтверждённые владельцем правила, [TASK-0006](tasks/TASK-0006-di850-paz.md).

**Текущая граница 29.09.2026:** ниже описаны эталоны DI850 и правила исходной книги. Их прежний встроенный FBD API отключён (`410`); текущий FBD требует подключённую библиотеку. ST назначений остаётся в `/api/mappings/generate`; детали — в [главе 02](02-current-implementation.md). Названия конкретного источника и ПАЗ не задают общую архитектуру: модель оборудования и входные адаптеры разделены в [SOURCE_LAYOUT.md](SOURCE_LAYOUT.md).

## Предметная область

Владелец уточнил: ПЛК 850 применяется в целевой ПАЗ, в которой нет AO. Это исключает AO850 из ожидаемых функций данного проекта, но не утверждает аппаратную невозможность AO для всех систем с CPU850. Для DI выбран исходный список `PS_IO_LIST_SCS_v4_new.xlsx` в соседнем `XML dev`. Отдельная книга с готовыми ST-формулами не требуется: назначения строятся из исходных столбцов по подтверждённым правилам.

Новые XML подтверждают **раздельную** реализацию DI: ST назначает физические входы модулю `D32V`, FBD распределяет выходы модуля в технологические `DDR_v1.C1`. Прямая физическая карточка FBD для CPU850 этими файлами не подтверждается.

Владелец дополнительно подтвердил: `Main_module → C1`, `Redundant_module → C2` того же DDR; имена брать из `Tag No` Excel без замены `LZS → LZSA`. Поддержка C2 основана на этом ответе и определении DDR в библиотеке, а не на нативном FBD-примере, где есть только C1.

## Проверенный состав эталонов

| Свойство | FBD | ST |
|---|---|---|
| POU | `DI_A11`, POUNum25 | `DI_A11_channels`, POUNum23 |
| Модули | 9: `A11-05`…`A11-13` | Те же 9, физические ID 5…13 |
| Состав | 234 блока, 225 связей, 234 карточки | 297 присваиваний: 9 статусов + 288 значений |
| Типы | `1933 / D32V_v1`, `885 / DDR_v1`, библиотека `TACSfbl` | Словари ISA отсутствуют |
| Физические блоки `GROBJTYPE=38` | Отсутствуют | Вместо графики — `STCODE` |

Оба файла: `VER=29`, `TENIX-CPU850`, `ControllerID=189312`, `ResuorceID=644`, `GroupID=19814`. DI-профиль использует их как начальный контекст; первый `POUNum` — 23 для ST и 25 для FBD. Эти числа — контекст конкретного экспорта, а не универсальные ID ПАЗ. Перед импортом нескольких POU необходимо задать свободные непересекающиеся диапазоны ST/FBD, соответствующие целевому проекту.

## Полная цепочка связей

```text
физический DI32.Measurement → ST: D32V.iNN → вызов D32V в FBD → D32V._NN → DDR_v1.C1
Quality канала0             → QUAL_STAT → ANY_TO_DWORD → D32V.Stat
```

В преобразовании исходной книги выход основного модуля направляется в C1, резервного — в C2. Оба поля используют одну карточку владельца DDR, включая расположение в разных POU.

Для каждого модуля ST содержит:

```st
MODULE.Stat := ANY_TO_DWORD (QUAL_STAT(_IO_I<ID>_DI32_0_VAL.Quality));
MODULE.i00 := _IO_I<ID>_DI32_0_VAL.Measurement;
(* ... *)
MODULE.i31 := _IO_I<ID>_DI32_31_VAL.Measurement;
```

`MODULE` — `_<PLC>_<модуль с подчёркиванием>`, например `_3000_S_SC_B01_A11_05`. Физический `<ID>` вводится явно, не выводится из суффикса слота. Внешние каналы — `0…31`, поля объекта — `i00…i31`. Статус назначается один раз на модуль, из Quality канала0, с обязательным по эталону приведением `ANY_TO_DWORD`. ST не вызывает DDR или D32; он заполняет поля существующих экземпляров.

Все 32 входа назначаются независимо от числа FBD-получателей. Это отличает DI от существующего разреженного ST AI/DO: пропущенный логический получатель не исключает физический канал из DI ST.

## FBD и карточки

- Модуль: `GROBJTYPE=37`, `IsaObjId=1933`, `CI=34`, `CO=33`, 100×700, `Info` равен имени экземпляра D32V.
- Получатель: `GROBJTYPE=31`, `IsaObjId=885`, `T11Text=".C1"`, `CI=1`, `CO=1`. Это объект `DDR_v1`, не BOOL и не `DV_v1`.
- Его `Block.Info = Card.Info + ".C1"`; карточка хранит имя владельца без суффикса. `IsRetain=-1`, `SSize=0`, `IV=6(FALSE),TRUE,1,2(FALSE),0,6(FALSE)`.
- Связь направлена из D32V `_NN` (выход `False`) в получателя на контакт `0` (вход `True`). Для DO направление обратное: логический тег → `D32V.iNN`.
- В FBD нет `_IO_*` карточек, `Measurement/Quality` блоков и аппаратных ModuleID. Транспортные T11ID/cardId не равны физическому ID.

Библиотека `libraries/all_lb_sinopec.xml`, `OBJTYPE ID=2061 / DDR`, определяет `DDR_C1` (`PARAM ID=3226`, `.C1`, «Входной сигнал №1») и `DDR_C2` (`PARAM ID=3227`, `.C2`, «Входной сигнал №2»). Оба имеют `VALTYPE=9`, `OFFSET=0`, `PGROUPID=-17170` и общего владельца `ISAOBJ ID=17170`, `DDR_v1`, `TACSfbl`, с тем же начальным значением. Генератор создаёт C2 с `T11Text=".C2"`, `Block.Info=Card.Info+".C2"`, общим `cardId` и общим `IV`. Отдельная карточка C2 не нужна. Наличие C3 в библиотеке не разрешает его использование: текущий DI-контракт принимает только C1/C2.

Непустой D32V `IV` найден только у одного экземпляра A11-07; остальные 8 пустые. Настройку одного экземпляра нельзя распространять на все модули. Текущий общий профиль D32V сохраняет пустой `IV`.

## Разреженность, резервы, повторы

Число связанных выходов модулей05…13: `32, 15, 32, 32, 32, 20, 27, 14, 21`. Например, A11-11 не содержит FBD-получателей на11…15, а A11-13 — на19. Номера нельзя уплотнять.

Реальные резервные DDR `_3010_GZY_10011.C1` и `_3010_GZY_10012.C1` привязаны к A11-13._08/_09: их надо сохранять. Пустой выход не создаёт новый BOOL/DDR автоматически. Добавленный пустой модуль требует D32V и все32 физических ST-входа, но не отдельных выдуманных получателей FBD.

Повторов одного DDR.C1 в эталоне нет. Два физических выхода одного ПЛК, пишущие в одно и то же поле DDR.C1 либо DDR.C2, отклоняются как неоднозначность без учёта регистра имени владельца. Пара C1/C2 одного DDR разрешена и разделяет карточку; разные ПЛК имеют отдельные пространства имён. Это не повторное ST-присваивание: ST пишет отдельные входы физических модулей.

## Исходная книга и правила преобразования

Выбранный владельцем файл — `../XML dev/PS_IO_LIST_SCS_v4_new.xlsx` относительно корня проекта, лист `PS_IO_LIST_SCS_v4`. Источник не находится в проектном `XML dev` и не подменяется одноимённой копией из `output/`. Ранее отмеченная пустота BL:BP остаётся фактом книги; после подтверждения владельца эти подготовленные поля не требуются для исходного DI-профиля.

| Поле источника | Правило |
|---|---|
| `I/O Type` | Для DI поддержаны `DIR(I)-NAMUR`, `DIR-VFC`, `DIR(SCS1)`; неизвестный DI-тип отклоняется. С TASK-0007 DO обрабатывается отдельной веткой; остальные направления пропускаются с предупреждением |
| `SCS` | Авторитетное имя ПЛК и пространство имён; `Cabinet` не заменяет его |
| `Tag No` | Владелец DDR: дефисы заменяются подчёркиваниями, добавляется начальное `_`; `LZS` не заменяется на `LZSA` |
| `Main_module` | Модуль DI32; его выход `_NN` подключается к `.C1` |
| `Redundant_module` | Резервный модуль DI32; его выход `_NN` подключается к `.C2` того же владельца |
| `Channel` | Исходный номер 0…31 без уплотнения пропусков |
| `Main_module2`, `Redundant_module2` | Не поддержаны; в DI-строках предоставленной книги стоят `-` |
| `SPARE` | Получатель DDR не создаётся; модуль сохраняется, пропуск отражается предупреждением |

В частности, A70/A71 относятся к SCS `3000_S_SC_B01`, несмотря на удалённый `Cabinet` 2202. Переносить эти модули в другой ПЛК по шкафу нельзя. Пустой по получателям DI-модуль допустим: FBD сохраняет D32, ST — все 32 значения и один статус.

В книге 619 DI-строк. Одна строка SPARE, №1578, соответствует каналу19 A11-13/A12-13; она не создаёт двух получателей. Оставшиеся 618 строк дают 1236 подключений C1/C2, 50 модулей, 8 групп POU и 3 ПЛК. При выборе всех групп без дополнительных модулей суммарно по трём XML FBD создаются 1286 блоков, 1236 связей и 668 карточек; ST — 1650 присваиваний. Это контрольные числа конкретной книги, не ограничения оборудования.

Сопоставление 225 нативных маршрутов C1 дало 213 точных совпадений и 12 расхождений имён `LZS`/`LZSA`. Владелец явно выбрал имена Excel; они сохраняются, без автоматического исправления по XML. Исходная книга и экспорты не перезаписываются.

## Входной контракт ядра

После разбора Excel нормализованный план должен содержать:

- группа: `Kind=DI`, `SCS=<имя ПЛК>`, `Prefix=A11`, `POUName=DI_A11`;
- модуль: `Name=A11-05`, `Type=DI32`, `ObjectType=D32V`, `Capacity=32`;
- существующий канал: исходный номер0…31, `Tag=<владелец DDR>`, `Member=C1` либо `C2`, строка источника и признак существующего резерва;
- DI-модуль без получателей: пустой `Channels`; он остаётся в FBD/ST. Для AI/DO пустой модуль по-прежнему недопустим;
- физический ID: отдельно для каждого выбранного модуля, только при генерации ST.

Контракт реализован в `PrepareSKZPlans` / `GenerateSKZ` и проверен тестами `skz_di_test.go`. DI ST допускает только CPU850 с Measurement/Quality; программный DI FBD не содержит физики и допускает оба CPU при наличии целевых библиотек. Прямой физический DI FBD основного рабочего пространства остаётся неподдержанным.

Исходная DI-книга загружается в разделе СКЗ через существующие `/api/skz/preview` и `/api/skz/generate`; подготовленные AI/DO-книги сохраняют прежний путь. Пользователь выбирает группы, количество модулей и физические ID для ST. UI допускает DI ST только с CPU850 и Measurement/Quality, а сервер и генератор проверяют то же ограничение. Лимит 4096 каналов DI ST считается по всем 32 физическим каналам каждого модуля, включая пустые; добавленные модули входят в лимит. Вопрос входного формата закрыт в Q-XML-007; импорт и исполнение остаются отдельной проверкой.
