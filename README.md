# XML Scheme Generator

Локальное Windows-приложение для преобразования шаблонов из экспортированных SCADA-библиотек в графические XML-файлы `BufScadaPOUS`.

Приложение написано на Go, не использует Python и после сборки запускается как один автономный `XmlSchemeGenerator.exe`. Один выходной файл может содержать несколько независимых `OnePOU`, а каждая POU — несколько технологических сигналов, построенных по выбранным библиотечным шаблонам.

Подробные правила преобразования библиотеки, карточек, блоков, связей и SCADA XML-диалекта зафиксированы в [промежуточной семантике интерпретации шаблонов](TEMPLATE_INTERPRETATION_SEMANTICS.md).

## Быстрый запуск

1. При необходимости скопируйте `config.example.json` в `config.json` и задайте параметры целевого проекта. Без локального `config.json` используются значения по умолчанию.
2. Поместите XML-библиотеки, включая `all_lb_sinopec.xml`, в `libraries/`.
3. Запустите `Start-XmlSchemeGenerator.cmd`.
4. Браузер откроет `http://127.0.0.1:3210`.
5. Добавьте POU, выберите тип I/O и общий библиотечный шаблон.
6. Добавьте физические модули и сигналы; канал каждого сигнала назначится по его позиции автоматически.
7. При необходимости измените шаблон отдельного сигнала или добавьте другие POU. Их настройки, модули и сигналы независимы.
8. Нажмите «Сформировать XML». Результат появится в `output/` и будет доступен для скачивания в интерфейсе.

Если `.exe` отсутствует, стартовый скрипт сначала запускает тесты и собирает его установленным Go SDK.

## Библиотеки и каталог шаблонов

Приложение читает XML-библиотеки непосредственно из `libraries/`. Большой экспорт `all_lb_sinopec.xml` обрабатывается потоково и не требует предварительного исправления исходного файла.

Некоторые vendor-экспорты содержат управляющие C0-символы, запрещённые XML 1.0. Во время чтения байты диапазона `0x00..0x1F`, кроме разрешённых `TAB`, `LF` и `CR`, потоково заменяются пробелами. Замена выполняется только в памяти:

- исходный файл библиотеки не перезаписывается;
- структура XML по-прежнему разбирается в строгом режиме;
- в каталоге показывается предупреждение с кодом и количеством замен.

Загрузка библиотеки и поддержка конкретного шаблона — разные состояния. Каталог показывает все найденные шаблоны, а для каждой библиотеки отдельно сообщает общее количество и количество совместимых с текущим генератором. Несовместимый шаблон остаётся видимым с причиной, но его генерация блокируется. Совместимость проверяется по поддерживаемым типам примитивов, разрешимости карточек, структуре связей и обязательным зависимостям блоков.

Для текущего локального `all_lb_sinopec.xml` тестами подтверждены загрузка 377 шаблонов и smoke-генерация всех 267 шаблонов, помеченных совместимыми. Эти значения не зашиты в интерфейс и пересчитываются при каждом обновлении каталога.

После добавления или замены XML нажмите «Обновить библиотеки».

## Модель выходного документа

Один `BufScadaPOUS` состоит из общей оболочки и одной или нескольких записей `POUS/OnePOU`.

Настройки каждой POU локальны для неё:

- `name`, `description`, `pouId`, `groupId`, `pouNumber`;
- размер страницы, `DPARAMS`, цвет фона и поля страницы;
- общий библиотечный шаблон, тип физического I/O и собственный набор модулей;
- упорядоченные списки сигналов внутри модулей;
- координаты каждого сигнала внутри этой POU.

`defaultTemplateKey` POU применяется ко всем её сигналам. Пустой `signal.templateKey` означает наследование, непустой — индивидуальное переопределение. Сигнал также задаёт `objectName`, режим имени, описание, `KLPath`, `offsetX` и `offsetY`. Карты исходных ID строятся отдельно для каждого экземпляра шаблона, поэтому один шаблон можно использовать многократно. При этом сгенерированные `T11ID` и `cardId` уникальны в пределах всего файла.

Канал физического сигнала не вводится вручную: это индекс сигнала внутри модуля. Поэтому после любой правки каналы всегда образуют последовательность `0, 1, 2, ...` без пропусков. Ёмкость одного модуля фиксирована профилем:

| Профиль | Физический тип | Каналов |
|---|---|---:|
| `DI` | `CDI32` | 32 |
| `DO` | `CDO32` | 32 |
| `AI` | `CAIH16V` | 16 |
| `AO` | `CAOH4V` | 4 |

Видимый ID модуля (`[8]`, `[41]` и т. п.) и внутренний ISA-префикс (`_IO_IU6`, `_IO_IU45`) — разные значения. Между ними в предоставленных экспортах нет общей формулы. ID по умолчанию назначаются как минимальные свободные `0, 1, 2, ...`; точный `bindingPrefix` можно задать в расширенных настройках модуля. Если он пуст, приложение использует явно помеченное предупреждением предположение `_IO_IU<ID>` для входов или `_IO_QU<ID>` для выходов.

Если координаты сигнала не заданы, применяется вертикальное авторазмещение с базовым offset `X=300`, `Y=100`: каждый следующий сигнал помещается ниже максимальной нижней границы уже размещённых с зазором `20`. Если исходная геометрия шаблона имеет отрицательные координаты, автоматический offset увеличивается, чтобы сохранить поля и не вывести примитивы за границу страницы. Явно заданный offset не компенсируется, относится только к своему сигналу и не переносится в другую POU.

Имена POU, POU ID и `POUNum` в одном документе должны быть уникальными. Производные имена ISA-карточек также не должны повторяться между сигналами одного файла.

## Как трактуется имя объекта

Имя программного модуля POU и имя экземпляра объекта — разные значения. Поле «Имя POU» записывается только в `OnePOU/@NAME` (например, `ADR_test`). Имя объекта (например, `_1110_LZIA_10101_ADR`) используется в `Block/@Info` и `ISACARDSINFO`.

В режиме `auto` приложение разрешает префиксы карточек через `ISAOBJLIST`. Например, для шаблона `ADR+AD3+HLB` ввод:

```text
_1110_LZIA_10101_ADR
```

распознаётся как карточка с префиксом `_ADR`, поэтому базовым именем станет `_1110_LZIA_10101`. Перед генерацией интерфейс показывает производные имена всех реально используемых выбранным шаблоном карточек.

Режим `base` запрещает автоматическое снятие суффикса. Корневая часть PLC-идентификатора канонизируется в верхний регистр так же, как в экспорте SCADA; регистр шаблонных полей `.Out`, `.Stat` и других при этом сохраняется.

## JSON API

Каталог доступен через `GET /api/templates`. Помимо `key`, запись шаблона содержит вычисленное поле `ioCapabilities` с подтверждёнными структурой шаблона профилями `AI`, `AO`, `DI`, `DO`.

Формат `POST /api/generate` создаёт несколько POU, физических модулей и сигналов в одном XML:

```json
{
  "fileName": "ad3_area",
  "t11Start": 3000000,
  "cardStart": 900000,
  "pous": [
    {
      "name": "AI_AREA_1",
      "description": "Аналоговые входы первой зоны",
      "pouId": 100000,
      "groupId": 19022,
      "pouNumber": 51,
      "defaultTemplateKey": "KEY_AD3_V2_ИЗ_API_TEMPLATES",
      "page": {
        "width": 2400,
        "height": 1800,
        "dparams": "3",
        "backgroundColor": "16777215",
        "marginRight": 200,
        "marginBottom": 200
      },
      "io": {
        "type": "AI",
        "modules": [
          {
            "id": 8,
            "bindingPrefix": "_IO_IU6",
            "signals": [
              {
                "objectName": "_1110_PI_10104_MAIN",
                "nameMode": "base",
                "description": "Давление"
              },
              {
                "templateKey": "KEY_СОВМЕСТИМОГО_OVERRIDE",
                "objectName": "_1110_FI_10402_MAIN",
                "nameMode": "base"
              }
            ]
          }
        ]
      }
    }
  ]
}
```

`fileName`, `t11Start` и `cardStart` относятся ко всему документу. Остальные настройки находятся внутри соответствующей POU, модуля или сигнала. Если `pouId` не указан, его значение равно начальному POU-курсору плюс индекс POU в массиве; ручной ID заменяет только свою позицию и не перенумеровывает последующие. Аналогично автоматический `POUNum` вычисляется от значения конфигурации и индекса. Пустой `module.id` получает минимальный свободный ID по всему документу, а повторяющиеся ручные ID запрещены.

Ограничения одного запроса: не более 128 POU, 4096 физических модулей, 4096 сигналов, 200 000 графических объектов и 100 000 карточек суммарно; размер JSON — до 8 МиБ. Каждый модуль должен содержать хотя бы один сигнал и не превышать ёмкость своего профиля.

### Совместимость старого API

Одиночный формат без поля `pous` сохранён:

```json
{
  "templateKey": "KEY_ИЗ_API_TEMPLATES",
  "objectName": "_1110_LZIA_10101_ADR",
  "pouName": "ADR_test",
  "nameMode": "auto",
  "description": "Тест",
  "klPath": "",
  "offsetX": 300,
  "offsetY": 100,
  "fileName": "adr_test",
  "pouGroupId": 19022,
  "pouNumber": 48
}
```

В одном запросе нельзя смешивать `pous` с legacy-полями POU или сигнала верхнего уровня. Внутри POU также нельзя одновременно задавать старый плоский `signals` и новый `io.modules`. Плоский список POU сохранён для обратной совместимости и не создаёт физической привязки. Глобальные `fileName`, `t11Start` и `cardStart` разрешены во всех форматах.

## Генерация

Поддерживаемое отображение примитивов:

- `31`, `34`, `35`, `36`, `37` → `Block`;
- `20` → `Link`;
- `1`, `2`, `7` → `OnePrim`.

Генератор:

- создаёт карточки только для фактически используемых `CARDID`;
- переносит `INITIALVALUE`, включая пустые значения и ведущий маркер `*`;
- сохраняет `CT=99` и маркеры ветвления `*` в маршрутах линий;
- переписывает все endpoint ID через новую карту `T11ID`;
- вычисляет рамку полилиний типа 7 по их `PointList`;
- формирует общие для документа `FONTSTYLES`, `ISAOBJSINFO` и `ISACARDSINFO`;
- перед записью проверяет количество объектов, уникальность ID и имён карточек, ссылки и строгую корректность XML.

Перед сериализацией блоки каждого сигнала стабильно упорядочиваются по зависимостям карточек: блок-владелец с пустым `T11Text` записывается раньше блоков `.Field` с тем же `cardId`.

Файл записывается в лексическом диалекте экспортёра SCADA: UTF-8 с BOM, компактно, без форматирующих text-node, с self-closing пустыми элементами, физическими CRLF внутри графических `PARAMS` и без пустой optional-секции `FONTSTYLES`.

Выход всегда формируется как корректный XML 1.0 UTF-8. Запрещённые XML 1.0 управляющие байты из входных vendor-библиотек в результат не копируются.

## Транспортные ID

Из библиотеки и имени объекта невозможно узнать занятые ID конкретной проектной базы. Поэтому автономный режим выделяет внутренне согласованные транспортные диапазоны из `data/state.json`.

Для всего выходного файла резервируются единые последовательные диапазоны `T11ID` и `cardId`; автоматические POU ID вычисляются от текущего POU-курсора с учётом позиции записи в документе. Порядок потребления диапазонов определяется порядком POU и сигналов в запросе. Начальные `t11Start` и `cardStart`, если они заданы, являются глобальными и не перезапускаются внутри каждой POU. Расчёт диапазона, генерация и валидация XML транзакционны: их ошибка не изменяет `state.json`; последующая запись готового файла в `output/` в эту транзакцию не входит. Автоматический курсор продвигается за наибольший фактически использованный POU ID. Каждый явный `pouId` также поднимает его при необходимости. Только диапазон, целиком лежащий ниже курсора, остаётся управляемым пользователем и не меняет состояние.

Перед импортом в существующий проект проверьте, поддерживает ли импортёр переназначение ID. Если требуются уже существующие project-specific ID, задайте начальные значения в расширенных параметрах либо используйте дополнительный экспорт целевого проекта.

## Конфигурация

Скопируйте `config.example.json` в локальный `config.json`, чтобы изменить порт, значения `Common`, настройки страницы и начальные диапазоны ID. Локальный файл исключён из Git, поскольку содержит параметры конкретной проектной базы.

Значения `config.page` служат базовыми для каждой POU. В новом формате их можно независимо переопределить через `pous[].groupId`, `pous[].pouNumber` и `pous[].page`. Параметры корневого `Common` остаются общими для всего `BufScadaPOUS`. Сервер слушает только loopback-адрес `127.0.0.1`.
