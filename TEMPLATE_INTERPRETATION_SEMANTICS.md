# Промежуточная семантика интерпретации шаблонов

Статус: промежуточная спецификация, редакция от 23.09.2026.

Документ фиксирует фактические правила преобразования библиотечного `TEMPLATE/grprim` в транспортный `BufScadaPOUS`, а также временные профили AO из TXT: FBD, ST и кадры диагностики `BufScada`, реализованные приложением XML Scheme Generator. Он предназначен как опорная спецификация для анализа следующих шаблонов и предотвращения возврата уже найденных ошибок импорта.

## 1. Уровни подтверждения

В документе используются три статуса:

- **Подтверждено импортом** — XML, созданный приложением, успешно импортирован в SCADA.
- **Закреплено реализацией** — правило выполняется кодом и проверяется автоматическими тестами, но не обязательно отдельно подтверждено ручным импортом для каждого поддерживаемого шаблона.
- **Открытый вопрос** — поведение известно не полностью либо зависит от целевого проекта.

Успешным импортом на текущем этапе подтверждены:

| Шаблон | ID | Рабочий результат | Статус |
|---|---:|---|---|
| `AD3_v2` | `17510` | `output/grob_grob_ad3v2.xml` | Подтверждено импортом |
| `ADR+AD3+HLB` | `19963` | `output/grob_grob_adr.xml` | Подтверждено импортом |

Эталонные материалы для сопоставления:

- `Library AD3_v2.xml` — исходная библиотека;
- `AD3 by Scada.xml` — нативный экспорт экземпляра `AD3_v2`;
- `ADR without input.xml` — нативный экспорт экземпляра `ADR+AD3+HLB`;
- `AD3 by GO application.xml` — результат до исправления общего XML-диалекта и порядка зависимостей.

Совокупность исправлений подтверждена успешным импортом. Какой именно отдельный лексический фактор первоначально вызывал исключение `String → Boolean`, отдельно A/B-тестом не изолировался.

## 2. Граница ответственности

Приложение выполняет пять связанных задач:

1. Потоково читает библиотеку, нормализует запрещённые XML 1.0 управляющие байты только в памяти и строит каталог.
2. Проверяет совместимость каждого шаблона с закрытым контрактом генератора.
3. Подставляет пользовательские имена объектов и независимый контекст каждой целевой POU.
4. Объединяет несколько экземпляров шаблонов и POU в согласованный транспортный граф с новыми `T11ID`, `cardId` и POU ID.
5. Сериализует граф в лексический XML-диалект, совместимый с legacy-импортёром SCADA.

Библиотека задаёт семантику блоков и графики, но не содержит достоверного контекста конкретного проекта: `Project`, `ControllerID`, `ResuorceID`, `GroupID`, `POUNum`, занятые транспортные ID и пользовательский `KLPath` должны поступать из конфигурации или формы генерации.

## 3. Конвейер преобразования

Преобразование составного документа выполняется в следующем порядке:

1. Разрешение всех `templateKey` для всех `pous[].signals[]` в одном снимке каталога.
2. Проверка совместимости выбранных шаблонов и расчёт единой потребности в транспортных ID.
3. Резервирование глобальных диапазонов `T11ID`, `cardId` и POU ID.
4. Для каждого сигнала — нормализация имени объекта, разрешение `CARDID`, классификация `grprim` и построение изолированной карты исходных ID.
5. Для каждой POU — применение её локальных параметров, координат и объединение графов сигналов.
6. Для всего документа — объединение `FONTSTYLES`, `ISAOBJSINFO` и `ISACARDSINFO` с проверкой конфликтов.
7. Формирование одной оболочки `BufScadaPOUS` с несколькими `POUS/OnePOU`.
8. Сериализация в SCADA-диалект и повторная проверка результата.

Ошибка на любом обязательном этапе прекращает генерацию; частичный XML не записывается.

### 3.1. Входная нормализация XML

XML-декодер остаётся строгим, но перед ним установлен потоковый фильтр для vendor-экспортов. Каждый байт меньше `0x20`, кроме разрешённых XML 1.0 `TAB` (`0x09`), `LF` (`0x0A`) и `CR` (`0x0D`), заменяется обычным пробелом.

Фильтр имеет узкую область действия:

- замена выполняется при чтении и не записывается обратно в библиотеку;
- исходный файл остаётся побайтно неизменным;
- исправляются только запрещённые C0-байты, а структурные ошибки XML не скрываются;
- код каждого заменённого символа и количество вхождений возвращаются как предупреждение библиотеки.

В предоставленном `all_lb_sinopec.xml` таким образом обрабатывается единичный `U+0012`. Это позволяет загрузить полный экспорт без ручной правки источника.

### 3.2. Каталог и совместимость

Каталог содержит все найденные `TEMPLATE`, но отдельно вычисляет флаг совместимости. Сводка библиотеки различает `templateCount` и `supportedTemplateCount`; запись шаблона содержит `supported` и список `warnings`.

Флаг `supported=false` устанавливается, в частности, для неизвестного `GROBJTYPE`, отсутствующей записи `CARDID` в `ISAOBJLIST`, некорректной структуры `FP`/`LP`/`PointList`, ссылки на блок вне шаблона или поля карточки без блока-владельца. Несовместимый шаблон остаётся доступным для анализа в каталоге, но сервер отвергает его до выделения выходного файла.

## 4. Имена POU и объекта

### 4.1. Имя программного модуля

`pouName` и имя экземпляра объекта имеют разную семантику.

```text
pouName    -> /BufScadaPOUS/POUS/OnePOU/@NAME
objectName -> Block/@Info и ISACARDSINFO/rec/@Info
```

Имя POU:

- не вычисляется из имени объекта;
- должно начинаться с Unicode-буквы или `_`;
- после первого символа допускает буквы, цифры и `_`;
- ограничено 160 Unicode-символами;
- при пустом API-значении строится как `POU_<имя шаблона>` с заменой недопустимых символов на `_`.

### 4.2. Корневое имя объекта

Введённое имя обрезается по краям и переводится в верхний регистр. Это воспроизводит канонический вид PLC-идентификаторов в экспортах SCADA:

```text
_1110_LZIA_10101_main -> _1110_LZIA_10101_MAIN
```

Регистр шаблонного суффикса поля не меняется:

```text
_1110_LZIA_10101_MAIN + .Out -> _1110_LZIA_10101_MAIN.Out
```

Допустимые символы корневого имени в текущей реализации: Unicode-буквы, цифры, `_`, `.` и `-`.

### 4.3. Автоматическое снятие префикса карточки

В режиме `auto` приложение собирает `EffectivePrefix` всех реально используемых карточек, сортирует их от самого длинного к самому короткому и проверяет окончание введённого имени.

`EffectivePrefix` определяется так:

```text
ISAOBJ/@Prefix, если атрибут непустой;
иначе ISAOBJ/PREFIX.
```

Пример для `ADR+AD3+HLB`:

```text
ввод:            _1110_LZIA_10101_ADR
найденный prefix: _ADR
baseName:         _1110_LZIA_10101
```

В режиме `base` суффикс не снимается.

## 5. ISA-карточки

Карточки создаются только для различных ненулевых `CARDID`, действительно встречающихся в примитивах выбранного шаблона. Неиспользуемые записи родительского `ISAOBJLIST` в результат не попадают.

Для каждой карточки:

```text
sourceCard = ISAOBJLIST/ISAOBJ[@ID = grprim/CARDID]
card.Info  = baseName + sourceCard.EffectivePrefix()
card.ID    = следующий транспортный cardId
```

`card.Name` формируется так:

1. Берётся пользовательское описание.
2. Если описание пустое, используется `card.Info`.
3. Если `ISAOBJ/DISC` непустой, он добавляется через пробел.

Остальные атрибуты:

| Выход | Источник или правило |
|---|---|
| `IsRetain` | всегда `1` |
| `SSize` | `ISAOBJ/SSIZE`, при пустом или нечисловом значении `0` |
| `KLPath` | пользовательское поле `klPath` |

Отсутствующий `CARDID` в `ISAOBJLIST` является фатальной ошибкой.

## 6. Классификация `grprim`

Поддерживаемое отображение является закрытым контрактом:

| `GROBJTYPE` библиотеки | Выходной элемент | Назначение в текущих шаблонах |
|---:|---|---|
| `31` | `ISAGraf/Blocks/Block` | поле или переменная |
| `34` | `ISAGraf/Blocks/Block` | константа |
| `35` | `ISAGraf/Blocks/Block` | оператор |
| `36` | `ISAGraf/Blocks/Block` | функциональный блок без экземплярной карточки |
| `37` | `ISAGraf/Blocks/Block` | экземпляр типизированного объекта |
| `20` | `ISAGraf/Links/Link` | связь |
| `1` | `GrObj/OnePrim` | текстовая графика |
| `2` | `GrObj/OnePrim` | прямоугольная графика |
| `7` | `GrObj/OnePrim` | полилиния или составной контур |

Любой следующий шаблон с другим `GROBJTYPE` отклоняется с указанием ID примитива. Неизвестный тип не преобразуется эвристически.

## 7. Семантика блоков

### 7.1. Основные атрибуты

| Выходное поле | Правило |
|---|---|
| `Block/@GROBJTYPE` | исходный `grprim/GROBJTYPE` |
| `Block/@T11ID` | новый транспортный ID после упорядочивания |
| `Graphics/@X`, `@Y` | исходные координаты плюс `offsetX`, `offsetY` |
| `Graphics/@WIDTH`, `@HEIGHT` | исходные размеры |
| `Params/@T11Text` | `[TEXT]` из `grprim/PARAMS` |
| `Params/@CI`, `@CO` | `[CI]`, `[CO]` |
| `Params/@VMODE` | `[VMODE]`, по умолчанию `0` |
| `Params/@Commented` | строго нормализованный `[COMMENT]` |
| `Params/@IsaObjId` | `grprim/OBJMSID` |
| `Params/@cardId` | новый ID разрешённой карточки или `0` |

Параметры вида `[KEY]=value` читаются построчно. Продолжение строки без нового `[KEY]` присоединяется к предыдущему параметру через `LF`.

### 7.2. Вычисление `Block/@Info`

Для блока с карточкой:

```text
если T11Text начинается с ".": Info = card.Info + T11Text
иначе:                           Info = card.Info
```

Для блока без карточки:

1. Используется непустой `grprim/TYPENAME`.
2. Если `TYPENAME` пуст и `GROBJTYPE=35`, известные операторы определяются по `OBJMSID`:

| `OBJMSID` | `Info` |
|---:|---|
| `-3` | `+` |
| `-4` | `/` |
| `-33` | `OR` |

3. В остальных случаях используется `[TEXT]`.

### 7.3. Начальное значение `IV`

Сохраняются три разных состояния:

| Состояние источника | Выход |
|---|---|
| значение отсутствует | узел `IV` отсутствует |
| значение присутствует, но пустое | `<IV/>` |
| непустое значение | `<IV>значение</IV>` |

Для блока с карточкой значение берётся из `ISAOBJ/INITIALVALUE`. Для блока без карточки используется собственный `grprim/IV`.

Значения переносятся буквально, включая составные структуры, `FALSE/TRUE`, даты, интервалы времени и ведущий маркер `*`.

### 7.4. Булева нормализация

Для `[COMMENT]` допустимы:

```text
true, 1, -1 -> true
false, 0, "" -> false
```

Регистр входа не важен. Любая другая лексема является ошибкой и больше не превращается молча в `false`.

### 7.5. Порядок владельца и полей карточки

Legacy-импортёр обрабатывает блоки последовательно. Поэтому для каждого ненулевого `cardId` определяющий блок должен встретиться раньше обращений к полям карточки.

Владелец определяется как блок, для которого одновременно выполняется:

```text
Block.Info == card.Info
T11Text == ""
```

Все остальные блоки с тем же `cardId` считаются зависимыми. Перед назначением `T11ID` выполняется стабильная топологическая сортировка `owner -> dependents`.

Для исходного порядка `AD3_v2`:

```text
.Out, .Stat, owner
```

формируется безопасный порядок:

```text
owner, .Out, .Stat
```

Между ними могут оставаться независимые блоки; полное нативное расположение SCADA не воспроизводится и не требуется. Отсутствующий владелец или цикл являются фатальной ошибкой.

Текущая реализация выбирает первого найденного владельца. Наличие двух владельцев одной карточки пока не отклоняется отдельно и отмечено как открытая проверка.

### 7.6. Подтверждённое исключение `AD3_HLB`

Только для шаблона `19963`, объекта `OBJMSID=18513`, типа `AD3_HLB` подтверждён нативным экспортом следующий override:

```text
CO < 17 -> CO = 17
```

Это не является общим обновлением всех версий `AD3_HLB`. В остальных шаблонах сохраняется сигнатура конкретного примитива, а расхождение с другими библиотечными сигнатурами выдаёт предупреждение.

## 8. Семантика связей

Для `GROBJTYPE=20` создаётся `Link`.

| Выход | Правило |
|---|---|
| `Negative` | всегда `false` |
| `asPointer` | всегда `false` |
| `UserEdit` | `true`, если `grprim/DRAWTYPE == 1`, иначе `false` |
| `Color` | `grprim/PENCOLOR` |
| `GetBitNum` | `[BN]`, по умолчанию `-1` |
| `ConvertTo` | `[CT]`, по умолчанию `0`; значение `99` сохраняется |
| `PointList/@PL` | `[PL]` со смещёнными координатами |

`PL` изменяется только в координатных парах `(x,y)`. Поэтому маркер ветвления `*`, разделители и завершающая `;` сохраняются.

`FP` и `LP` разбираются через `SplitN(..., 4)` и должны дать четыре части:

```text
oldBlockID | direction | port | rectangle
```

Преобразование endpoint:

1. `oldBlockID` заменяется через карту старого ID в новый `T11ID`.
2. `0` или `false` нормализуется в `False`.
3. `-1` или `true` нормализуется в `True`.
4. Имя порта сохраняется.
5. Служебный rectangle канонизируется в `0,0,100,20`.

Дополнительные разделители `|` внутри четвёртой части не анализируются, поскольку исходный rectangle всё равно заменяется. Ссылка на отсутствующий блок или неизвестное направление запрещает генерацию.

Связь потребляет один транспортный `T11ID`, хотя сам этот ID в элементе `Link` не сериализуется.

## 9. Графические примитивы

Для типов `1`, `2` и `7` создаётся `GrObj/OnePrim`.

Переносятся:

- `OBJTYPE`, `GRNUM`, `DRAWTYPE`;
- `PenParams`, `PenColor`, `BrushColor`, `GradColor`;
- `ScriptName` из `grprim/NAME`;
- текст `PARAMS`;
- размеры и координаты.

`X` и `Y` сдвигаются на пользовательский offset. Если в `PARAMS` есть `[PL]`, каждая координата списка также сдвигается.

Для `OBJTYPE=7` `X/Y/WIDTH/HEIGHT` пересчитываются по фактическим точкам `PL`, поскольку именно полилиния считается авторитетной геометрией. Это безопасная реализованная интерпретация, но служебный bounding box может отличаться от странных значений старого нативного экспорта.

Переносы строк внутри текстового `PARAMS` в итоговом файле записываются физическими `CRLF`.

## 10. Шрифты и таблица ISA-типов

### 10.1. `FONTSTYLES`

Обрабатываются только `FONTID` графических примитивов. Значения `""` и `65535` означают встроенный пользовательский шрифт и отдельной записи не требуют.

Для прочих ID:

1. Используется корневая запись библиотечного `FONTSTYLES`.
2. Если её нет, стиль восстанавливается из `[USERFONT]=size;name;param;color;`.
3. Неустранимое отсутствие `FONTID`/`USERFONT` даёт предупреждение.

Для известных восстановленных стилей используются имена:

```text
81 -> Заголовок 1
83 -> Комментарий в коде
```

Записи сортируются по числовому ID. Если итоговых стилей нет, секция `FONTSTYLES` полностью отсутствует, а не выводится пустой.

### 10.2. `ISAOBJSINFO`

Секция строится из уникальных положительных `OBJMSID` поддерживаемых блоков:

```text
rec/@ID      = OBJMSID
rec/@Info    = TYPENAME
rec/@LibName = LIBNAME
```

Одинаковый ID с противоречивыми `Info` или `LibName` является ошибкой. Записи сортируются по ID.

## 11. Транспортные идентификаторы

Начальные значения хранятся в `data/state.json`. Под блокировкой рассчитываются следующие диапазоны, затем XML генерируется и проверяется, и только после этого новое состояние фиксируется:

- единый диапазон `T11ID` для всех сигналов документа;
- единый диапазон `cardId` для всех сигналов документа;
- автоматические POU ID для тех `OnePOU`, где `pouId` не задан.

Пользователь может переопределить глобальные начальные `t11Start` и `cardStart` в расширенных параметрах. Эти значения относятся ко всему `BufScadaPOUS` и не перезапускаются для каждой POU. Конкретный `pouId` при необходимости задаётся локально в записи POU; иначе ID равен начальному POU-курсору плюс индекс POU в документе. Расчёт диапазона, генерация и валидация образуют одну транзакцию: при их ошибке `state.json` не изменяется; запись уже готового `output/*.xml` происходит после фиксации state. Курсоры T11/card становятся максимумом прежнего значения и конца фактически выбранного диапазона. POU-курсор продвигается за наибольший реально использованный автоматический или ручной POU ID. Поэтому полностью нижний ручной диапазон остаётся ответственностью пользователя, а пересекающий курсор диапазон продвигает состояние своим концом.

Внутри одного сигнала фактический порядок назначения `T11ID`:

1. Топологически упорядоченные `Block`.
2. Скрытые слоты `Link`.
3. `OnePrim`.

Сигналы потребляют диапазоны последовательно в порядке POU и в порядке сигналов внутри POU. Карта исходных ID каждого экземпляра шаблона изолирована, поэтому одинаковые библиотечные ID могут повторяться в разных сигналах, а созданные ID во всём документе остаются уникальными.

Этот порядок является внутренним транспортным соглашением приложения, а не универсальной семантикой SCADA. В нативном AD3 графические ID встречались раньше ID блоков, а в ADR — позже. Гарантируются уникальность и корректное переписывание ссылок, но не совпадение чисел или глобального порядка с исходным проектом.

Все ID должны быть положительными и помещаться в signed 32-bit. При импорте в существующую базу ответственность за отсутствие конфликтов остаётся у целевого процесса импорта.

## 12. Оболочка POU и контекст проекта

| Выход | Источник |
|---|---|
| `Common/@VER` | `config.common.version`, иначе версия библиотеки |
| `Common/@Project` | `config.common.project` |
| `Common/@ControllerTypeName` | `config.common.controllerTypeName` |
| `Common/@ControllerID` | `config.common.controllerId` |
| `Common/@ResuorceID` | `config.common.resourceId` |
| `OnePOU/@ID` | `pous[].pouId` или следующий транспортный POU ID |
| `OnePOU/@NAME` | `pous[].name` |
| `OnePOU/@GroupID` | `pous[].groupId` или `config.page.groupId` |
| `OnePOU/@POUNum` | `pous[].pouNumber` или последовательное значение от `config.page.pouNumber` |
| `OnePOU/@isFBD` | `1` |
| `OnePOU/@Enabled` | `1` |
| `OnePOU/@Disc` | пустая строка |

Один корневой `BufScadaPOUS` содержит массив `POUS/OnePOU`. `Common` и корневые словари общие для файла, но внутренний контекст каждой POU независим:

- имя и описание;
- POU ID, `GroupID` и `POUNum`;
- `DPARAMS`, размеры и цвет страницы, правое и нижнее поля;
- собственный список сигналов;
- координаты сигналов и итоговая область страницы.

Ручные `pouId`, `GroupID` и `POUNum` должны быть положительными signed 32-bit. Имена POU, POU ID и `POUNum` не могут повторяться в одном файле. Пустые/нулевые portable-значения конфигурации пока разрешены, но сопровождаются предупреждением.

Каждый сигнал внутри POU задаёт `templateKey`, `objectName`, `nameMode`, описание, `KLPath` и необязательные `offsetX`/`offsetY`. Один и тот же шаблон допускается использовать многократно с разными именами объектов. Повтор производного `Card.Info` во всём документе считается ошибкой, поскольку `ISACARDSINFO` является общей таблицей.

При отсутствии координат базовый offset первого сигнала равен `X=300`, `Y=100`. Если минимальная координата исходной геометрии отрицательна, вычисленный offset дополнительно компенсирует её. Следующий сигнал автоматически располагается ниже максимальной нижней границы уже размещённых шаблонов с зазором `20`. Явный offset не компенсируется, влияет только на свой сигнал и участвует в расчёте позиции следующих сигналов этой же POU; авторазмещение другой POU начинается независимо.

Размер каждой страницы вычисляется как максимум между её локальным или конфигурационным значением и геометрией всех сигналов этой POU с учётом offset и правого/нижнего полей.

Новый API представляет эту модель как `pous[].signals[]`. Legacy-запрос без `pous`, с одиночными `templateKey`, `objectName` и `pouName` верхнего уровня, сохраняется и создаёт одну POU с одним сигналом. Смешивать обе формы в одном запросе нельзя; `fileName`, `t11Start` и `cardStart` остаются глобальными в обоих режимах.

Текущий `config.json` настроен по `AD3 by Scada.xml`. При смене проекта его значения нельзя считать универсальными.

## 13. Лексический XML-диалект SCADA

Нативный экспорт показал, что импортёр нельзя считать обычным XML-инфосетным потребителем. Поэтому приложение использует отдельный централизованный token serializer.

Обязательный контракт:

- UTF-8 BOM `EF BB BF`;
- XML declaration `encoding="UTF-8"`;
- компактное тело без форматирующих отступов и межэлементных text-node;
- любой пустой элемент записывается как `<X/>`, а не `<X></X>`;
- полезные переносы в character data записываются как физические `CRLF`, не как `&#xA;`;
- пустая optional-секция `FONTSTYLES` опускается;
- обязательные пустые `Gotos` и `Links` сохраняются как `<Gotos/><Links/>`;
- в конце файла записывается перевод строки.

Булевы лексемы разделены по контексту:

| Контекст | Допустимый выход |
|---|---|
| `isCut`, `isFFB`, `Commented`, `Negative`, `asPointer`, `UserEdit` | `true` / `false` |
| `isFBD`, `Enabled`, `IsRetain` | `0` / `1` |
| направление внутри `FP`/`LP` | `False` / `True` |

Перед записью валидатор проверяет этот контракт, включая отсутствие expanded-empty элементов и форматирующих text-node.

## 16. Открытые вопросы и ограничения

1. Успешный ручной импорт подтверждён пока для двух из восьми шаблонов.
2. Точный одиночный триггер прежнего `String → Boolean` не выделен; подтверждена работоспособность полного набора исправлений.
3. Два владельца одного `cardId` пока не считаются отдельной ошибкой — используется первый.
4. Нативный полный порядок независимых блоков не воспроизводится; гарантируется только порядок зависимостей.
5. `cleanNumber` использует fallback для пустых и некорректных числовых параметров; для новых библиотек желательно отдельно проверить отсутствие повреждённых чисел.
6. Нативные файлы могут содержать запрещённые XML 1.0 управляющие байты: библиотечный загрузчик заменяет их пробелом только во входном потоке, а генератор намеренно не создаёт такие байты и принимает пользовательский `KLPath` только в XML-совместимом виде.
7. `Project`, контроллер, ресурс, `GroupID` и `POUNum` являются контекстом целевого проекта и не выводятся из семантики шаблона.
8. Транспортные ID не гарантированно свободны в произвольной существующей базе.
9. Пересчёт bounding box для `OBJTYPE=7` основан на авторитетности `PL`; отдельного нативного подтверждения для всех полилиний нет.
10. Различающиеся сигнатуры одного типа между legacy-шаблонами не унифицируются автоматически, кроме подтверждённого случая шаблона 19963.
11. Эталонные файлы `AD3 by Scada.xml` и `ADR without input.xml` пока не подключены к тестам как golden fixtures; полное семантическое сопоставление с ними выполнено анализом и ручным импортом.
12. Составные документы с несколькими сигналами и POU закреплены автоматическими тестами, но их ручной импорт в SCADA отдельно не отмечен как подтверждённый.
13. Один API-запрос ограничен 128 POU, 4096 сигналами, 200 000 `grprim`, 100 000 карточек и 8 МиБ JSON; размеры и поля каждой страницы ограничены 1 000 000. Имена POU/объекта ограничены 160 Unicode-символами, описания и `KLPath` — 500.

## 17. Критерии принятия следующего шаблона

Перед признанием нового шаблона поддержанным необходимо:

1. Убедиться, что каждый `grprim` относится к поддерживаемому классу.
2. Проверить разрешимость всех ненулевых `CARDID` через родительский `ISAOBJLIST`.
3. Проверить наличие владельца перед зависимыми полями каждой карточки.
4. Проверить допустимость `COMMENT`, `FP`, `LP`, `PL`, `CI`, `CO`, `VMODE`, `BN` и `CT`.
5. Проверить три состояния `IV` и составные `INITIALVALUE`.
6. Проверить шрифты и наличие пригодного `USERFONT` для отсутствующих стилей.
7. Запустить полный набор тестов.
8. Сгенерировать XML с корректным контекстом целевого проекта.
9. Сопоставить семантику с нативным экспортом, если он доступен.
10. Выполнить контрольный импорт в SCADA и добавить результат в таблицу подтверждённых шаблонов.

До прохождения последнего шага шаблон считается поддержанным реализацией, но не подтверждённым импортом.

## 18. Физические модули AI/AO/DI/DO

Основание раздела — нативные экспорты `AI_GRAF.xml`, `AO_GRAF.xml`, `DI_GRAF.xml` и `DO_GRAF.xml`. Структура исходных графов подтверждена сравнением с `all_lb_sinopec.xml`; создаваемые приложением физические привязки пока имеют статус «закреплено реализацией» до отдельного контрольного импорта.

### 18.1. Модель POU, модуля и канала

POU задаёт `defaultTemplateKey`. Пустой `templateKey` сигнала наследует это значение, непустой является локальным override. Физические сигналы вложены в модуль, а номер канала равен индексу сигнала в массиве модуля. Номер канала не принимается из API и поэтому всегда последователен.

| Профиль | Физический тип | Ёмкость модуля |
|---|---|---:|
| `AI` | `CAIH16V` | 16 |
| `AO` | `CAOH4V` | 4 |
| `DI` | `CDI32` | 32 |
| `DO` | `CDO32` | 32 |

ID физического модуля является пользовательским идентификатором, а не `T11ID`, `cardId` или POU ID. Незаполненные ID назначаются как минимальные свободные неотрицательные значения по всему документу; дубликаты запрещены.

### 18.2. Видимый ID и внутренний ISA-префикс

Нативные данные доказывают, что видимый ID в `Card.Name` и внутренний адрес в `Card.Info` независимы:

| Экспорт | Видимое имя | `Card.Info` |
|---|---|---|
| AI | `[8] CAIH16V > канал N` | `_IO_IU6_N` |
| AO | `[11] CAOH4V > канал N` | `_IO_QU29_N` |
| DI | `[41] CDI32 > канал N` | `_IO_IU45_N` |
| DO | `[43] CDO32 > канал N` | `_IO_QU48_N` |

Универсальной функции `moduleId -> bindingPrefix` по этим значениям нет. Поэтому модель хранит отдельный `bindingPrefix`, например `_IO_IU6`. При пустом значении допускается только явно предупреждаемое предположение `_IO_IU<ID>` для AI/DI и `_IO_QU<ID>` для AO/DO. Перед импортом такой fallback необходимо сверить с целевым проектом.

Для физического канала формируются:

```text
Card.Info = bindingPrefix + "_" + channel
Card.Name = "[" + moduleId + "] " + physicalType + " > канал " + channel
Block.Info = Card.Name + T11Text
```

Последнее правило намеренно отличается от обычных библиотечных блоков, использующих `Card.Info`: нативные блоки типа `38` отображают человекочитаемое имя физического канала. Физическая карточка имеет `IsRetain=-1`, `SSize=0`; её `KLPath` пуст и не наследуется от технологического объекта. `IsaObjId` физических ссылок (`17679` или `17706`) не добавляется в `ISAOBJSINFO`, что соответствует всем четырём экспортам.

### 18.3. Профиль AI

На занятый канал создаётся одна физическая карточка и два блока `GROBJTYPE=38` с общим `cardId`:

```text
.ValueDINT: IsaObjId=17679, CI=0, CO=1 -> AD3_v2.Xin
.Status:    IsaObjId=17679, CI=0, CO=1 -> AD3_v2.Xs
```

Прямое подключение разрешается только при единственном владельце `OBJMSID=17480` и свободных входах `Xin` и `Xs`. В исследованной библиотеке этому условию отвечают шаблоны `17510`, `18555` и `19962`. Один AI-канал требует дополнительно два блока, две связи, одну карточку и четыре позиции общего диапазона T11.

### 18.4. Профиль AO

Нативный `AO_GRAF.xml` состоит из библиотечного `AN_JMP` (`TEMPLATE 17625`) и добавленной физической записи:

```text
REAL_TO_DINT.Result -> .ValueDINT
.ValueDINT: GROBJTYPE=38, IsaObjId=17679, CI=1, CO=1
```

Преобразователь, `.Xmin` и `.Xmax` уже входят в совместимый библиотечный шаблон и повторно не синтезируются. Привязка допустима только при единственном `REAL_TO_DINT` со свободным выходом `Result`; это подтверждено для `17625 AN_JMP` и `19967 AN_AO`. Один AO-канал добавляет блок, связь, карточку и две позиции T11.

### 18.5. Профили DI и DO

Один цифровой модуль содержит экземпляр `D32V_v1` (`IsaObjId=1933`, `CI=34`, `CO=33`) и все 32 физические карточки, даже если часть технологических каналов не назначена. Это воспроизводит нативные DI/DO-экспорты.

Направление DI:

```text
physical.Value -> D32V_v1.iNN
D32V_v1._NN -> logical field, port 0
```

Направление DO:

```text
logical field, port 0 -> D32V_v1.iNN
D32V_v1._NN -> physical.Value
```

Физический `.Value` имеет `IsaObjId=17706`; у DI параметры `CI=0, CO=1`, у DO — `CI=1, CO=1`. Логическая точка выбирается только при единственном карточном блоке `GROBJTYPE=31`, `CI=1`, `CO=1` со свободным требуемым направлением порта `0`. Ноль или несколько кандидатов считаются несовместимым либо неоднозначным шаблоном и приводят к ошибке до создания файла.

Фиксированная стоимость цифрового модуля: 65 позиций T11 и 33 карточки — один `D32V_v1`, 32 физических блока и 32 связи между физикой и D32. Каждый назначенный технологический сигнал добавляет ещё одну связь и одну позицию T11 сверх собственных объектов библиотечного шаблона.

### 18.6. Граница доказанного поведения

Нативные DI/DO-файлы используют самостоятельные ссылки `GROBJTYPE=31` на уже существующие карточки технологических объектов, тогда как приложение создаёт выбранный библиотечный экземпляр и подключает его единственную совместимую граничную карточку. Для шаблонов без однозначной границы автоматическое угадывание запрещено. Если позднее потребуется подключать конкретное поле сложного шаблона, контракт должен быть расширен явным идентификатором anchor-примитива и подтверждён отдельным нативным экспортом.

## 19. Временный генератор AO из табличного TXT

Основание — `XML dev/A11_00_example.xml` и `XML dev/AO_excell_import_scheme.txt`. Это отдельный профиль нативного графического экспорта; библиотечный профиль AO из раздела 18.4 к нему не применяется.

### 19.1. Структура контрольного XML

Корень содержит `Common`, `POUS`, `ISAOBJSINFO`, `ISACARDSINFO`. Единственный `OnePOU` содержит `PARAMS`, `ISAGraf`, `GrObj`. Внутри `ISAGraf` находятся `Blocks`, `Gotos`, `Links`; последние два элемента и `GrObj` пусты и записываются self-closing. Секция `FONTSTYLES` отсутствует.

В файле 56 самостоятельных блоков и 56 карточек: модули `A11-00..A11-13`, по четыре канала. Все блоки имеют одну сигнатуру:

| Поле | Значение |
|---|---|
| `Block.GROBJTYPE` | `37` |
| `Block.Info` | имя экземпляра, равное `Card.Info` |
| `Params.T11Text` | пустая строка |
| `Params.CI`, `Params.CO` | `7`, `2` |
| `Params.VMODE`, `Params.Commented` | `0`, `false` |
| `Params.IsaObjId` | `888` |
| `Params.IV` | `,,,100.0` |
| `Graphics` | `X=500`, `Y=50+190*i`, `WIDTH=100`, `HEIGHT=160` |
| `Card.Name` | имя экземпляра + ` Аналоговая нагрузка` |
| `Card.IsRetain`, `Card.SSize`, `Card.KLPath` | `-1`, `0`, пустая строка |

`ISAOBJSINFO` содержит единственную запись `ID=888`, `Info=AN_v1`, `LibName=TACSfbl`. Присутствуют только владельцы экземпляров; в исходном XML нет ни `.OUT`-ссылок, ни `REAL_TO_DINT`, ни физических блоков типа `38`, ни графических линий или комментариев.

`IsRetain=-1` в этом экспорте принадлежит обычным владельцам `AN_v1`. Поэтому правило «любая карточка с `-1` обязательно физическая» неприменимо к данному профилю. Это подтверждённое исключение для `GROBJTYPE=37`, `IsaObjId=888`, а не основание менять retain всех библиотечных объектов.

### 19.2. Разбор карты и сохранение каналов

TXT представляет таблицу с разделителями TAB. Для определения позиции используются `FCS`, `Module`, `Channel`, а технологический тег извлекается из аргумента `.OUT` в `DCS AO`. Поля `Main_module`, `Redundant_module`, `I/O Type` и `Тип объекта` описывают исходную карту; контрольный файл содержит только тип `AN_v1`.

Пример:

```text
FCS = 3000_D_SC_B01
Module = A11-00
Channel = 0
DCS AO = _IO_QU*A11-00*_0.ValueDINT := REAL_TO_DINT(_3107_TV_64101A.OUT, 0.0, 100.0);
```

даёт экземпляр `_3107_TV_64101A` в позиции `A11-00 / 0`. Адрес слева и номер канала должны согласовываться с полями строки. Две разные записи в одной позиции не могут молча заменять друг друга.

Ключ POU — пара `(FCS, префикс Module до дефиса)`. Нативный пример называет группу A11 `AO_A11_00`; после уточнения пользователя генератор назначает короткие имена `AO_A11`, `AO_A12` и т. д. FCS не включается в имя POU: различие контроллеров сохраняется отдельными XML-файлами. Все реально присутствующие модули группы объединяются в одну POU, включая резервирующие модули. Отдельные префиксы A11 и A12 образуют разные POU. Между разными FCS также нет объединения, даже если имена модулей, POU или тегов совпадают.

В каждом представленном модуле выводятся каналы `0..3` в исходной нумерации. Отсутствующая в карте позиция получает резервное имя:

```text
reserveTag = "_" + FCS + "_" + replace(Module, "-", "_") + "_" + Channel
```

Например, `_3000_D_SC_B01_A11_00_3`. Суффиксы FCS вроде `B05_1` сохраняются. Отсутствующие модули не достраиваются: наличие `A30-13` само по себе не создаёт `A30-00..A30-12`.

### 19.3. Повторные теги и транспортные ID

Контрольный TXT содержит 410 назначенных позиций и 207 уникальных технологических тегов: 203 тега встречаются дважды в основном и резервирующем модулях, четыре — по одному разу. Такое повторение предусмотрено картой и не является повторной записью одного канала.

По результатам импорта пользователь подтвердил: резервирующие повторения уже подключены непосредственно в ST; второй графический вызов вызывает сообщение «Найден, но уже используется другим функциональным блоком». Поэтому одинаковый технологический тег внутри одного FCS получает ровно один блок-владелец и одну запись `ISACARDSINFO`. Предпочитается позиция, чей модуль соответствует `Main_module`; при отсутствии такого назначения выбирается первая позиция в стабильном порядке модулей и каналов. Порядок строк в TXT не должен случайно переносить владельца в резервирующий модуль. Тот же тег в другом FCS независим и получает свой блок и карточку в отдельном файле.

Все остальные появления тега помечаются в плане как `duplicate=true`; исходный `tag` и ссылка `duplicateOf` на выбранную позицию сохраняются для предпросмотра. При сериализации на этих местах не создаётся ничего: ни `Block`, ни замещающей резервной карточки, ни декоративного объекта. Расчёт координат сохраняет все четыре позиции модуля: `Y=50+190*positionIndex`, включая пропущенные дубликаты. Следующие блоки не сдвигаются в образовавшийся пробел. Обычная отсутствующая позиция остаётся отдельным случаем и получает резерв по правилу раздела 19.2. Уникальные резервные карточки не объединяются с технологическими тегами.

Нативные `T11ID` образуют последовательность `1826208..1826263`, а `cardId` имеют формулу `634800 + 16*moduleIndex + channel`. Шаг карточек отражает исходную базу; он не является требованием формата. При генерации выделяются согласованные уникальные ID только для фактически создаваемых блоков и карточек; пустые повторные позиции ID не расходуют. Ссылки блоков обновляются вместе с карточками; `IsaObjId=888` сохраняет значение идентификатора типа.

### 19.4. Контекст, объём и границы профиля

Начальный `Common` берётся из контрольного экспорта: `VER=29`, `isCut=false`, `isFFB=false`, `ControllerTypeName=TENIX-CPU715`, `ControllerID=189300`, `ResuorceID=637`; `Project` также является контекстом исходной базы. Эти поля доступны для настройки под целевой проект.

Нативная POU имеет `ID=19525`, `GroupID=19498`, `Enabled=1`, `isFBD=1`, `POUNum=36`, пустой `Disc`. Страница: `DPARAMS=3`, `HEIGHT=12000`, `WIDTH=2000`, `SHABLONPAGEID=0`, `FONCOLOR=16777215`, `PRINTWIDTH=1944`, `PRINTHEIGHT=1363`, `PRINTPAGEA4=8`. Транспортные ID и номера POU должны оставаться уникальными в создаваемом документе.

Для всей контрольной карты группировка даёт 8 XML-файлов по FCS, 21 POU и 128 модулей. После дополнения свободных каналов сохраняются 512 позиций: 207 уникальных технологических блоков, 102 резерва и 203 пустых повторных места. Получается `207 + 102 = 309` блоков и столько же карточек. Для A11 отдельно — одна POU, 14 модулей и 56 позиций: 23 технологических блока, 10 резервов и 23 пустых повтора; всего 33 блока и 33 карточки. API сохраняет `summary.signalCount` как число позиций, а `summary.blocks` и `summary.cards` — как фактические объекты. Отдельный `summary.skippedDuplicateCount` сообщает число пустых повторных позиций.

Поддерживаемые границы преобразования из TXT — `min=0`, `max=100`, подтверждённые нативным `IV=,,,100.0`. Парсер извлекает и показывает другие числовые границы, однако генератор отклоняет их: перенос произвольной шкалы в поля `AN_v1` не подтверждён образцом. Каждый XML имеет единый `Common`; генерация разбивает карту по FCS, а передача нескольких FCS непосредственно генератору одного документа отклоняется. Расширенные параметры задают также общий `GroupID` и первый `POUNum`; `POUNum` начинается заново в каждом файле. Транспортные ID на весь набор файлов выделяются действующим счётчиком приложения.

Уточнение по целевому импортёру: по сообщению пользователя SCADA переназначает числовые ID и сопоставляет сущности по именам. Генератор не выводит числовые ID контроллеров из FCS и не добавляет неподтверждённые XML-атрибуты маршрутизации. Имя FCS включается в имя файла (`AO_import_3000_D_SC_B01.xml`); файл следует импортировать в соответствующий ПЛК. Имена экземпляров и резервов из карты не меняются при сокращении имени POU. Диалог «Не найден в контроллере/ресурсе — создать экземпляр?» относится к наличию самого тега, а не к формату имени POU.

Символьная запись `_IO_QU*A11-00*_0` не содержит реального числового префикса физического канала. Генератор этого профиля не подставляет предполагаемые `_IO_QU<ID>`, не добавляет преобразователь или физические связи и не интерпретирует текст присваивания как готовый граф FBD. Результат представляет графические экземпляры `AN_v1` согласно нативному образцу. Создание физической привязки потребует отдельного подтверждённого соответствия модулей адресам целевого проекта.

## 20. Дополнительная генерация ST для групп AO

Основание — нативные `output/AO_A11_channels.xml` и `output/AO_A12_channels.xml`, предоставленные отдельно от графического образца. Это новый режим временного генератора. Правила FBD из раздела 19, включая пустые повторные позиции, не меняются.

### 20.1. Нативный ST XML

Корень `BufScadaPOUS` содержит только `Common` и `POUS`. Каждая `OnePOU` содержит только `STCODE`: без `PARAMS`, `ISAGraf`, `GrObj`, `ISAOBJSINFO`, `ISACARDSINFO` и `FONTSTYLES`. Значение `isFBD="0"` отличает ST от графической POU; `Enabled="1"`. Имя `OnePOU.NAME`, например `AO_A11_channels`, повторяется после `PROGRAM` внутри STCODE.

В исходниках сохранён тот же контекст `Common`: `VER=29`, `ControllerTypeName=TENIX-CPU715`, `ControllerID=189300`, `ResuorceID=637`, `isCut=false`, `isFFB=false`. Для A11 указаны `ID=19545`, `GroupID=19498`, `POUNum=38`; для A12 — `ID=19654`, `GroupID=19498`, `POUNum=40`. Эти транспортные значения не определяют адреса выходов в ST.

STCODE — обычный XML-текст, не CDATA. Нативные файлы записаны UTF-8 без BOM, с физическими CRLF. Код начинается с `PROGRAM <имя POU>` и заканчивается `END_PROGRAM`; между группами из четырёх присваиваний есть пустая строка. Нет секции `VAR` или создания экземпляров. При сериализации XML-спецсимволы экранируются, а переносы строк внутри кода сохраняются как CRLF.

### 20.2. Соответствие модулей физическим ID

Каждый выбранный модуль даёт ровно четыре строки:

```text
_IO_QU<moduleID>_<channel>.ValueDINT := REAL_TO_DINT(<tag>.OUT, <min>, <max>);
channel = 0, 1, 2, 3
```

Например, `_IO_QU41_0` означает физический адрес с ID `41` и каналом `0`; это не транспортный ID POU или карточки. TXT содержит только символическое соответствие `_IO_QU*A12-03*_0`, поэтому число `41` задаётся пользователем. Встроенные начальные ID `0, 1, 2, ...` — заполняемые значения, которые необходимо сверить с реальной конфигурацией, а не результат извлечения из TXT.

Нативные соответствия подтверждены сравнением всех строк с картой:

| POU | Исходные модули | Физические ID | Присваивания | Назначения из TXT | Резервные каналы | Повторные назначения |
|---|---|---|---:|---:|---:|---:|
| `AO_A11_channels` | `A11_00..A11_13` | `24..37` | 56 | 46 | 10 | 23 |
| `AO_A12_channels` | `A12_00..A12_03` | `38..41` | 16 | 10 | 6 | 5 |

ID уникальны среди всех выбранных модулей одного FCS, включая разные POU: иначе два модуля записывали бы в одинаковые `_IO_QU<ID>_<channel>`. Разные FCS экспортируются отдельно и могут иметь одинаковые ID. Не допускаются отсутствующие, `null`, отрицательные, дробные и выходящие за допустимый целочисленный диапазон ID. Количество ID должно совпадать с числом модулей.

### 20.3. Количество модулей и повторные теги

Настройки каждой выбранной POU содержат её ключ `(FCS, Prefix)`, число модулей и упорядоченный список физических ID. Исходные модули сохраняют имена и числовой порядок; список ID сопоставляется с этим порядком. Число модулей нельзя уменьшить ниже числа представленных в карте, чтобы не удалять назначения незаметно для пользователя.

При увеличении количества новые модули добавляются после максимального существующего суффикса. Каждый новый модуль содержит четыре резервных тега по формуле раздела 19.2. Пропуски в исходных номерах не достраиваются: количество — число модулей, а не верхняя граница их имён. Новые резервные экземпляры должны быть предварительно созданы в целевой SCADA или отдельно представлены графически; один ST-текст их не создаёт.

`Channel.Duplicate` означает только пустую позицию графического профиля. ST использует сохранённые `Tag`, `Min`, `Max` всех каналов, включая повторные назначения основных и резервирующих модулей. Поэтому один технологический тег может читаться в нескольких выражениях `.OUT`, записывающих в разные физические адреса. Это не повторное создание графического блока-владельца и не требует второй карточки экземпляра.

Для всей контрольной карты исходные 128 модулей дают 512 присваиваний: 410 назначений из TXT, включая 203 повторных, и 102 резервных канала. FBD той же карты остаётся равен 309 блокам и 309 карточкам с 203 пустыми повторными позициями. ST не создаёт графические карточки и не расходует диапазоны `T11ID`/`cardId`; ему требуются только транспортные ID POU.

`min/max` переносятся из разобранного выражения TXT. Для ST допустимы проверенные конечные числа с `min < max`; FBD-ограничение `0..100`, связанное с полями экземпляра `AN_v1`, здесь не применяется. У резервов, отсутствовавших в TXT, используются границы `0.0, 100.0`.

### 20.4. Экспорт, API и границы проверки

Состав ST-экспорта выбирается явно: после загрузки TXT все POU выключены. Интерфейс группирует их по ПЛК (FCS), показывает отдельные флажки POU и общий флажок ПЛК с промежуточным состоянием при частичном выборе. Массовые команды выбирают или снимают все POU. Настройки количества модулей и ID сохраняются при переключении выбора и режима; новая карта начинает новый выбор. При пустом выборе создание XML заблокировано, сервер также отклоняет пустой список POU.

Для выбранных POU формируются отдельные XML по FCS, с именами файлов вида `AO_import_ST_3000_D_SC_B01.xml`. Имя ST-POU имеет вид `AO_<Prefix>_channels` и не конфликтует с графической POU `AO_<Prefix>`. Каждый файл имеет собственный общий контекст `Common`; пользователь импортирует его в соответствующий ПЛК. Настройки транспортного контекста не заменяют ручную проверку физических ID.

Маршрут `POST /api/temporary/ao/generate-st` принимает `multipart/form-data`: файл карты `file`, имя результата `fileName`, JSON `context` и JSON `st`. Последний содержит `pous[]` с полями `groupKey`, `moduleCount`, `moduleIds`; например, `groupKey="3000_D_SC_B01:A12"`, `moduleCount=4`, `moduleIds=[38,39,40,41]`. Невыбранные группы не экспортируются; параметры количества и физических ID относятся только к своей выбранной POU. Предпросмотр исходных тегов и признак графического повтора не означают пропуск соответствующей ST-строки.

Генератор не выполняет ST, не проверяет доступность аппаратуры и не загружает код в контроллер. Проверки XML, формата присваиваний и совпадения с предоставленными нативными исходниками не заменяют проверку импорта и конфигурации целевой SCADA.

## 21. Кадры диагностики AO панели оператора

Основание — нативный `output/diagnostic.xml` с кадром `AO_B01_A12_00_AOC4H` и прежняя TXT-карта AO. Профиль встроен в приложение: файл из `output/` служит материалом сравнения, а не обязательным входным файлом при работе. Это отдельный формат страниц панели оператора, не разновидность программной POU.

Пользователь уточнил, что привязки тегов в контрольном XML устарели. Поэтому структура кадра берётся из XML, а актуальные назначения — из TXT. Наличие в старом примере четырёх имён `_3000_D_SC_B01_A12_00_0..3` не означает, что занятые каналы следует заменять резервными именами.

### 21.1. Нативная оболочка и геометрия

Корень `BufScada` содержит секции в порядке `Common`, `Pages`, `COLORSTYLES`, `CARDSINFO`, `PAGEMSINFO`. Пространств имён нет. `Common` включает `VER` и `Project`; `ControllerID`, `ResuorceID`, `GroupID`, `POUS`, `ISAGraf` и STCODE этому профилю не принадлежат. Связь с конкретным ПЛК записана в символьных путях `CARDSINFO`, а не предполагается из числового ID контроллера.

Один `Pages/OnePage` соответствует одному физическому модулю, например `A11_02`. Его атрибут `ID` совпадает с дочерним `<ID>`. Основные параметры страницы воспроизводят образец: `WIDTH=1200`, `HEIGHT=152`, `DPARAMS=66`, `GRIDSIZE=10`, `FONCOLOR=536870913`, `SHABLONPAGEID=0`, `FORMARKA=0`, `PRINTWIDTH=600`, `PRINTHEIGHT=800`, `PRINTPAGEA4=8`, `FRAMENUM=5`, `SREZ=1`, `NUM=0`. Сохраняются пустые служебные элементы, в том числе `EXDATA`, `DISC`, `LAYERS` и `SCRIPTCODE`.

В `PageLayers` находится один видимый слой `Num=1`. Его исходное имя переносится буквально, без попытки угадать исправление необычных Unicode-символов нативного экспорта. На слое пять `OnePrim` с `OBJTYPE=8`:

| Назначение | Координаты | Размер | `ObjMSID` | `CardID` |
|---|---|---|---:|---|
| Фон и заголовки | `X=0`, `Y=0` | `1200×152` | `3655` | `0` |
| Канал 0 | `X=70`, `Y=54` | `1080×24` | `3679` | Карточка тега канала 0 |
| Канал 1 | `X=70`, `Y=78` | `1080×24` | `3679` | Карточка тега канала 1 |
| Канал 2 | `X=70`, `Y=102` | `1080×24` | `3679` | Карточка тега канала 2 |
| Канал 3 | `X=70`, `Y=126` | `1080×24` | `3679` | Карточка тега канала 3 |

Служебный `PARAMS` каждого примитива содержит `[MODE]=-1`, пустой `[TEXT]`, `[FONTID]=0`, `[USERFONT]=8;Arial;0;0;` с физическими CRLF. Нативный файл — UTF-8 без BOM. Сериализатор сохраняет компактную XML-структуру, self-closing пустые элементы и буквальный текст параметров, а не превращает секции в экранированные XML-строки.

### 21.2. Таблицы ссылок и принадлежность ПЛК

Фиксированные `ObjMSID` разрешаются общей секцией `PAGEMSINFO`:

```text
3679 -> 2//(AN_v1)/(8x_Diag_МФК1500_HART_AO)
3655 -> 2//(AI_DIAG16_AD3v1_kvit)/(8x_AO_4_DIAG)
```

Эти представления подтверждены также в `all_lb_sinopec.xml`. Они не встраиваются в результат: импорт должен разрешить их в целевой SCADA. Секция `COLORSTYLES` сохраняет нативную запись `ID=2`, `Name="Фон мнемосхемы"`, `Color=14935011`.

Для строк каналов таблица `CARDSINFO` имеет формат:

```text
OnePrim/CardID -> CARDSINFO/rec/@ID
CARDSINFO/rec/@CardInfo = 2/<FCS>/<resourceNumber>/<Channel.Tag>/(AN_v1)
```

Например, `2/3000_D_SC_B01/1/_3101_PV_61012A/(AN_v1)`. Номер ресурса по умолчанию `1` — часть пути разрешения экземпляра, не транспортный `ResuorceID=637` из `BufScadaPOUS` и не физический `_IO_QU<ID>`. Диагностический `context` состоит только из строковых `version`, `project`, `resourceNumber`; параметры FBD/ST сюда не подмешиваются.

Все четыре строки используют `Channel.Tag` актуального плана, включая назначения с `Duplicate=true`. Отсутствующий канал получает резерв по формуле раздела 19.2. Повторение технологического тега в основном и резервирующем модуле остаётся видимым на обоих кадрах: это две ссылки на существующий экземпляр, а не два FBD-блока-владельца. В пределах одного FCS такой тег имеет одну запись `CARDSINFO`, на которую ссылаются несколько примитивов. В другом FCS тег независим; контроллеры не объединяются в общий выходной файл.

### 21.3. Группировка кадров, имена и выбор

Единица кадра — `(FCS, Module)`, в отличие от единицы программной POU `(FCS, Prefix)`. Поэтому `A11_02` и `A11_03` — два кадра одного ПЛК; `A12_00` — ещё один кадр того же ПЛК. Каждый кадр содержит четыре канала своего модуля, без перенумерации или объединения основного и резервирующего модуля.

```text
controllerPart = часть FCS после "_SC_", иначе полное FCS
frameName = "AO_" + controllerPart + "_" + Module + "_AOC4H"
```

Нормализованный `Module` использует подчёркивание. Примеры: `AO_B01_A11_02_AOC4H`, `AO_B01_A11_03_AOC4H`, `AO_B05_1_A51_00_AOC4H`. Суффиксы контроллера `_1`, `_2` сохраняются и не сводятся к одному `B05` или `B07`.

Интерфейс предлагает выбрать ПЛК, изначально выбор пуст. Доступны массовые команды выбора и снятия всех ПЛК. Для каждого выбранного FCS экспортируются все представленные в TXT модули и только они, в отдельный XML. Настройки выбора, количества модулей и физических ID ST не определяют диагностику: добавленные только в ST резервные модули не появляются в диагностических кадрах автоматически. Выбор режимов независим; новая TXT-карта начинает новый выбор.

### 21.4. Транспортные ID, API и объём

Диагностика использует три независимых пространства новых транспортных ID: `SourceT11ID` примитивов, ID карточек и Page ID. Page ID выделяются счётчиком `NextPage` с начальным значением `1000000`; `OnePOU.ID` и его курсор не расходуются. При чтении старого `data/state.json`, где Page-курсор ещё отсутствует, добавляется только его начальное значение: существующие курсоры T11/card/POU не сбрасываются. Генерация и проверки всего набора файлов завершаются до фиксации новых диапазонов.

Маршрут `POST /api/temporary/ao/generate-diagnostic` принимает `multipart/form-data`: `file`, `fileName`, JSON `context` и JSON `diagnostic`. Пример выбора:

```json
{"fcs":["3000_D_SC_B01","3000_D_SC_B02"]}
```

Предпросмотр использует общий `POST /api/temporary/ao/preview`, не создаёт файлов и не расходует ID. Применяются прежние ограничения временного генератора: файл до 2 МиБ и не более 4096 позиций каналов в разобранной карте.

Пустой выбор, неизвестный FCS или повторный ключ выбора отклоняются. Для выбранных контроллеров формируются файлы `<fileName>_diagnostic_<FCS>.xml`. Ответ имеет `kind="diagnostic"`, список файлов и агрегированную сводку: `frameCount` — число кадров, `graphics` — число примитивов, `signalCount` — число строк каналов, `cards` — число уникальных карточек; `pouCount=0`.

Вся контрольная карта даёт 8 XML-файлов, 128 кадров, 512 строк каналов, 640 примитивов и 309 карточек. Все 203 повторных назначения видны на соответствующих кадрах, в отличие от пустых повторных мест FBD. Один кадр всегда расходует пять T11 ID и один Page ID; потребность в карточках определяется числом уникальных тегов внутри выбранного FCS.

Границы профиля: поддержана диагностика AO с объектами `AN_v1` и указанными двумя библиотечными представлениями. Другие семейства диагностических кадров AI/DI/DO не выводятся автоматически из этого примера. Выход содержит ссылки на существующие объекты и представления, а не определения новых библиотечных типов или экземпляров. Проверка XML и соответствия структуры образцу закрепляет реализацию, но не означает подтверждённый импорт нового результата в SCADA; импорт и разрешение ссылок проверяются отдельно в целевом проекте.
