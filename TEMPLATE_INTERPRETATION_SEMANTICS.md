# Промежуточная семантика интерпретации шаблонов

Статус: промежуточная спецификация, редакция от 01.09.2026.

Документ фиксирует фактические правила преобразования библиотечного `TEMPLATE/grprim` в транспортный `BufScadaPOUS`, реализованные приложением XML Scheme Generator. Он предназначен как опорная спецификация для анализа следующих шаблонов и предотвращения возврата уже найденных ошибок импорта.

## 1. Уровни подтверждения

В документе используются три статуса:

- **Подтверждено импортом** — XML, созданный приложением, успешно импортирован в SCADA.
- **Закреплено реализацией** — правило выполняется кодом и проверяется автоматическими тестами, но не обязательно отдельно подтверждено ручным импортом для каждого из восьми шаблонов.
- **Открытый вопрос** — поведение известно не полностью либо зависит от целевого проекта.

Успешным импортом на текущем этапе подтверждены:

| Шаблон | ID | Рабочий результат | Статус |
|---|---:|---|---|
| `AD3_v2` | `17510` | `output/grob_grob_ad3v2.xml` | Подтверждено импортом |
| `ADR+AD3+HLB` | `19963` | `output/grob_grob_adr.xml` | Подтверждено импортом |

Эталонные материалы для сопоставления:

- `Library AD3_v2.xml` — исходная библиотека;
- `AD3 by Scada.xml` — нативный экспорт экземпляра `AD3_v2`;
- `ADR without input.xml` — нативный экспорт экземпляра `ADR+AD3+HLB`;
- `AD3 by GO application.xml` — результат до исправления общего XML-диалекта и порядка зависимостей.

Совокупность исправлений подтверждена успешным импортом. Какой именно отдельный лексический фактор первоначально вызывал исключение `String → Boolean`, отдельно A/B-тестом не изолировался.

## 2. Граница ответственности

Приложение выполняет четыре независимые задачи:

1. Извлекает структуру шаблона и используемые ISA-карточки из библиотеки.
2. Подставляет пользовательское имя объекта и контекст целевого POU.
3. Строит согласованный транспортный граф с новыми `T11ID`, `cardId` и POU ID.
4. Сериализует граф в лексический XML-диалект, совместимый с legacy-импортёром SCADA.

Библиотека задаёт семантику блоков и графики, но не содержит достоверного контекста конкретного проекта: `Project`, `ControllerID`, `ResuorceID`, `GroupID`, `POUNum`, занятые транспортные ID и пользовательский `KLPath` должны поступать из конфигурации или формы генерации.

## 3. Конвейер преобразования

Преобразование выполняется в следующем порядке:

1. Выбор `TEMPLATE` и его родительского `OBJTYPE`.
2. Нормализация имени объекта и вычисление базового имени.
3. Разрешение фактически используемых `CARDID` через `ISAOBJLIST`.
4. Создание будущих записей `ISACARDSINFO`.
5. Классификация каждого `grprim` как `Block`, `Link` или `OnePrim`.
6. Топологическое упорядочивание блоков: владелец карточки раньше обращений к её полям.
7. Назначение новых транспортных ID и переписывание ссылок.
8. Перенос геометрии, параметров, `IV`, шрифтов и ISA-типов.
9. Формирование оболочки `BufScadaPOUS`.
10. Сериализация в SCADA-диалект и повторная проверка результата.

Ошибка на любом обязательном этапе прекращает генерацию; частичный XML не записывается.

## 4. Имена POU и объекта

### 4.1. Имя программного модуля

`pouName` и имя экземпляра объекта имеют разную семантику.

```text
pouName    -> /BufScadaPOUS/POUS/OnePOU/@NAME
objectName -> Block/@Info и ISACARDSINFO/rec/@Info
```

Имя POU:

- не вычисляется из имени объекта;
- должно начинаться с Unicode-буквы или `_`;
- после первого символа допускает буквы, цифры и `_`;
- ограничено 160 Unicode-символами;
- при пустом API-значении строится как `POU_<имя шаблона>` с заменой недопустимых символов на `_`.

### 4.2. Корневое имя объекта

Введённое имя обрезается по краям и переводится в верхний регистр. Это воспроизводит канонический вид PLC-идентификаторов в экспортах SCADA:

```text
_1110_LZIA_10101_main -> _1110_LZIA_10101_MAIN
```

Регистр шаблонного суффикса поля не меняется:

```text
_1110_LZIA_10101_MAIN + .Out -> _1110_LZIA_10101_MAIN.Out
```

Допустимые символы корневого имени в текущей реализации: Unicode-буквы, цифры, `_`, `.` и `-`.

### 4.3. Автоматическое снятие префикса карточки

В режиме `auto` приложение собирает `EffectivePrefix` всех реально используемых карточек, сортирует их от самого длинного к самому короткому и проверяет окончание введённого имени.

`EffectivePrefix` определяется так:

```text
ISAOBJ/@Prefix, если атрибут непустой;
иначе ISAOBJ/PREFIX.
```

Пример для `ADR+AD3+HLB`:

```text
ввод:            _1110_LZIA_10101_ADR
найденный prefix: _ADR
baseName:         _1110_LZIA_10101
```

В режиме `base` суффикс не снимается.

## 5. ISA-карточки

Карточки создаются только для различных ненулевых `CARDID`, действительно встречающихся в примитивах выбранного шаблона. Неиспользуемые записи родительского `ISAOBJLIST` в результат не попадают.

Для каждой карточки:

```text
sourceCard = ISAOBJLIST/ISAOBJ[@ID = grprim/CARDID]
card.Info  = baseName + sourceCard.EffectivePrefix()
card.ID    = следующий транспортный cardId
```

`card.Name` формируется так:

1. Берётся пользовательское описание.
2. Если описание пустое, используется `card.Info`.
3. Если `ISAOBJ/DISC` непустой, он добавляется через пробел.

Остальные атрибуты:

| Выход | Источник или правило |
|---|---|
| `IsRetain` | всегда `1` |
| `SSize` | `ISAOBJ/SSIZE`, при пустом или нечисловом значении `0` |
| `KLPath` | пользовательское поле `klPath` |

Отсутствующий `CARDID` в `ISAOBJLIST` является фатальной ошибкой.

## 6. Классификация `grprim`

Поддерживаемое отображение является закрытым контрактом:

| `GROBJTYPE` библиотеки | Выходной элемент | Назначение в текущих шаблонах |
|---:|---|---|
| `31` | `ISAGraf/Blocks/Block` | поле или переменная |
| `34` | `ISAGraf/Blocks/Block` | константа |
| `35` | `ISAGraf/Blocks/Block` | оператор |
| `36` | `ISAGraf/Blocks/Block` | функциональный блок без экземплярной карточки |
| `37` | `ISAGraf/Blocks/Block` | экземпляр типизированного объекта |
| `20` | `ISAGraf/Links/Link` | связь |
| `1` | `GrObj/OnePrim` | текстовая графика |
| `2` | `GrObj/OnePrim` | прямоугольная графика |
| `7` | `GrObj/OnePrim` | полилиния или составной контур |

Любой следующий шаблон с другим `GROBJTYPE` отклоняется с указанием ID примитива. Неизвестный тип не преобразуется эвристически.

## 7. Семантика блоков

### 7.1. Основные атрибуты

| Выходное поле | Правило |
|---|---|
| `Block/@GROBJTYPE` | исходный `grprim/GROBJTYPE` |
| `Block/@T11ID` | новый транспортный ID после упорядочивания |
| `Graphics/@X`, `@Y` | исходные координаты плюс `offsetX`, `offsetY` |
| `Graphics/@WIDTH`, `@HEIGHT` | исходные размеры |
| `Params/@T11Text` | `[TEXT]` из `grprim/PARAMS` |
| `Params/@CI`, `@CO` | `[CI]`, `[CO]` |
| `Params/@VMODE` | `[VMODE]`, по умолчанию `0` |
| `Params/@Commented` | строго нормализованный `[COMMENT]` |
| `Params/@IsaObjId` | `grprim/OBJMSID` |
| `Params/@cardId` | новый ID разрешённой карточки или `0` |

Параметры вида `[KEY]=value` читаются построчно. Продолжение строки без нового `[KEY]` присоединяется к предыдущему параметру через `LF`.

### 7.2. Вычисление `Block/@Info`

Для блока с карточкой:

```text
если T11Text начинается с ".": Info = card.Info + T11Text
иначе:                           Info = card.Info
```

Для блока без карточки:

1. Используется непустой `grprim/TYPENAME`.
2. Если `TYPENAME` пуст и `GROBJTYPE=35`, известные операторы определяются по `OBJMSID`:

| `OBJMSID` | `Info` |
|---:|---|
| `-3` | `+` |
| `-4` | `/` |
| `-33` | `OR` |

3. В остальных случаях используется `[TEXT]`.

### 7.3. Начальное значение `IV`

Сохраняются три разных состояния:

| Состояние источника | Выход |
|---|---|
| значение отсутствует | узел `IV` отсутствует |
| значение присутствует, но пустое | `<IV/>` |
| непустое значение | `<IV>значение</IV>` |

Для блока с карточкой значение берётся из `ISAOBJ/INITIALVALUE`. Для блока без карточки используется собственный `grprim/IV`.

Значения переносятся буквально, включая составные структуры, `FALSE/TRUE`, даты, интервалы времени и ведущий маркер `*`.

### 7.4. Булева нормализация

Для `[COMMENT]` допустимы:

```text
true, 1, -1 -> true
false, 0, "" -> false
```

Регистр входа не важен. Любая другая лексема является ошибкой и больше не превращается молча в `false`.

### 7.5. Порядок владельца и полей карточки

Legacy-импортёр обрабатывает блоки последовательно. Поэтому для каждого ненулевого `cardId` определяющий блок должен встретиться раньше обращений к полям карточки.

Владелец определяется как блок, для которого одновременно выполняется:

```text
Block.Info == card.Info
T11Text == ""
```

Все остальные блоки с тем же `cardId` считаются зависимыми. Перед назначением `T11ID` выполняется стабильная топологическая сортировка `owner -> dependents`.

Для исходного порядка `AD3_v2`:

```text
.Out, .Stat, owner
```

формируется безопасный порядок:

```text
owner, .Out, .Stat
```

Между ними могут оставаться независимые блоки; полное нативное расположение SCADA не воспроизводится и не требуется. Отсутствующий владелец или цикл являются фатальной ошибкой.

Текущая реализация выбирает первого найденного владельца. Наличие двух владельцев одной карточки пока не отклоняется отдельно и отмечено как открытая проверка.

### 7.6. Подтверждённое исключение `AD3_HLB`

Только для шаблона `19963`, объекта `OBJMSID=18513`, типа `AD3_HLB` подтверждён нативным экспортом следующий override:

```text
CO < 17 -> CO = 17
```

Это не является общим обновлением всех версий `AD3_HLB`. В остальных шаблонах сохраняется сигнатура конкретного примитива, а расхождение с другими библиотечными сигнатурами выдаёт предупреждение.

## 8. Семантика связей

Для `GROBJTYPE=20` создаётся `Link`.

| Выход | Правило |
|---|---|
| `Negative` | всегда `false` |
| `asPointer` | всегда `false` |
| `UserEdit` | `true`, если `grprim/DRAWTYPE == 1`, иначе `false` |
| `Color` | `grprim/PENCOLOR` |
| `GetBitNum` | `[BN]`, по умолчанию `-1` |
| `ConvertTo` | `[CT]`, по умолчанию `0`; значение `99` сохраняется |
| `PointList/@PL` | `[PL]` со смещёнными координатами |

`PL` изменяется только в координатных парах `(x,y)`. Поэтому маркер ветвления `*`, разделители и завершающая `;` сохраняются.

`FP` и `LP` разбираются через `SplitN(..., 4)` и должны дать четыре части:

```text
oldBlockID | direction | port | rectangle
```

Преобразование endpoint:

1. `oldBlockID` заменяется через карту старого ID в новый `T11ID`.
2. `0` или `false` нормализуется в `False`.
3. `-1` или `true` нормализуется в `True`.
4. Имя порта сохраняется.
5. Служебный rectangle канонизируется в `0,0,100,20`.

Дополнительные разделители `|` внутри четвёртой части не анализируются, поскольку исходный rectangle всё равно заменяется. Ссылка на отсутствующий блок или неизвестное направление запрещает генерацию.

Связь потребляет один транспортный `T11ID`, хотя сам этот ID в элементе `Link` не сериализуется.

## 9. Графические примитивы

Для типов `1`, `2` и `7` создаётся `GrObj/OnePrim`.

Переносятся:

- `OBJTYPE`, `GRNUM`, `DRAWTYPE`;
- `PenParams`, `PenColor`, `BrushColor`, `GradColor`;
- `ScriptName` из `grprim/NAME`;
- текст `PARAMS`;
- размеры и координаты.

`X` и `Y` сдвигаются на пользовательский offset. Если в `PARAMS` есть `[PL]`, каждая координата списка также сдвигается.

Для `OBJTYPE=7` `X/Y/WIDTH/HEIGHT` пересчитываются по фактическим точкам `PL`, поскольку именно полилиния считается авторитетной геометрией. Это безопасная реализованная интерпретация, но служебный bounding box может отличаться от странных значений старого нативного экспорта.

Переносы строк внутри текстового `PARAMS` в итоговом файле записываются физическими `CRLF`.

## 10. Шрифты и таблица ISA-типов

### 10.1. `FONTSTYLES`

Обрабатываются только `FONTID` графических примитивов. Значения `""` и `65535` означают встроенный пользовательский шрифт и отдельной записи не требуют.

Для прочих ID:

1. Используется корневая запись библиотечного `FONTSTYLES`.
2. Если её нет, стиль восстанавливается из `[USERFONT]=size;name;param;color;`.
3. Неустранимое отсутствие `FONTID`/`USERFONT` даёт предупреждение.

Для известных восстановленных стилей используются имена:

```text
81 -> Заголовок 1
83 -> Комментарий в коде
```

Записи сортируются по числовому ID. Если итоговых стилей нет, секция `FONTSTYLES` полностью отсутствует, а не выводится пустой.

### 10.2. `ISAOBJSINFO`

Секция строится из уникальных положительных `OBJMSID` поддерживаемых блоков:

```text
rec/@ID      = OBJMSID
rec/@Info    = TYPENAME
rec/@LibName = LIBNAME
```

Одинаковый ID с противоречивыми `Info` или `LibName` является ошибкой. Записи сортируются по ID.

## 11. Транспортные идентификаторы

Начальные значения хранятся в `data/state.json` и резервируются перед генерацией:

- диапазон `T11ID`;
- диапазон `cardId`;
- один POU ID.

Пользователь может переопределить начальные значения в расширенных параметрах.

Фактический порядок назначения `T11ID`:

1. Топологически упорядоченные `Block`.
2. Скрытые слоты `Link`.
3. `OnePrim`.

Этот порядок является внутренним транспортным соглашением приложения, а не универсальной семантикой SCADA. В нативном AD3 графические ID встречались раньше ID блоков, а в ADR — позже. Гарантируются уникальность и корректное переписывание ссылок, но не совпадение чисел или глобального порядка с исходным проектом.

Все ID должны быть положительными и помещаться в signed 32-bit. При импорте в существующую базу ответственность за отсутствие конфликтов остаётся у целевого процесса импорта.

## 12. Оболочка POU и контекст проекта

| Выход | Источник |
|---|---|
| `Common/@VER` | `config.common.version`, иначе версия библиотеки |
| `Common/@Project` | `config.common.project` |
| `Common/@ControllerTypeName` | `config.common.controllerTypeName` |
| `Common/@ControllerID` | `config.common.controllerId` |
| `Common/@ResuorceID` | `config.common.resourceId` |
| `OnePOU/@ID` | транспортный POU ID |
| `OnePOU/@NAME` | отдельное имя POU |
| `OnePOU/@GroupID` | request override или `config.page.groupId` |
| `OnePOU/@POUNum` | request override или `config.page.pouNumber` |
| `OnePOU/@isFBD` | `1` |
| `OnePOU/@Enabled` | `1` |
| `OnePOU/@Disc` | пустая строка |

`GroupID` и `POUNum` можно переопределить для одной генерации. Неположительное ручное значение запрещено. Пустые/нулевые portable-значения конфигурации пока разрешены, но сопровождаются предупреждением.

Размер страницы вычисляется как максимум между значением конфигурации и размером шаблона с учётом offset и правого/нижнего полей.

Текущий `config.json` настроен по `AD3 by Scada.xml`. При смене проекта его значения нельзя считать универсальными.

## 13. Лексический XML-диалект SCADA

Нативный экспорт показал, что импортёр нельзя считать обычным XML-инфосетным потребителем. Поэтому приложение использует отдельный централизованный token serializer.

Обязательный контракт:

- UTF-8 BOM `EF BB BF`;
- XML declaration `encoding="UTF-8"`;
- компактное тело без форматирующих отступов и межэлементных text-node;
- любой пустой элемент записывается как `<X/>`, а не `<X></X>`;
- полезные переносы в character data записываются как физические `CRLF`, не как `&#xA;`;
- пустая optional-секция `FONTSTYLES` опускается;
- обязательные пустые `Gotos` и `Links` сохраняются как `<Gotos/><Links/>`;
- в конце файла записывается перевод строки.

Булевы лексемы разделены по контексту:

| Контекст | Допустимый выход |
|---|---|
| `isCut`, `isFFB`, `Commented`, `Negative`, `asPointer`, `UserEdit` | `true` / `false` |
| `isFBD`, `Enabled`, `IsRetain` | `0` / `1` |
| направление внутри `FP`/`LP` | `False` / `True` |

Перед записью валидатор проверяет этот контракт, включая отсутствие expanded-empty элементов и форматирующих text-node.

## 14. Подтверждённые шаблоны

### 14.1. Текущий каталог библиотеки

Все восемь шаблонов проходят генерацию и автоматические проверки. Ручной импорт пока подтверждён только для строк, отмеченных в последнем столбце.

| ID | Шаблон | Blocks | Links | OnePrim | Cards | Всего `grprim` | Ручной импорт |
|---:|---|---:|---:|---:|---:|---:|---|
| `17509` | `AD3_v2_REGZONE` | 33 | 25 | 1 | 9 | 59 | не подтверждён |
| `17510` | `AD3_v2` | 7 | 0 | 2 | 3 | 9 | подтверждён |
| `18402` | `ADR+AD3_REGZONE` | 31 | 27 | 1 | 7 | 59 | не подтверждён |

## 15. Автоматические инварианты

Текущие тесты прогоняют все восемь шаблонов библиотеки и для каждого проверяют:

- полное сохранение количества примитивов по классам;
- количество фактически используемых карточек;
- уникальность новых `T11ID`;
- существование всех блоков, на которые ссылаются endpoint;
- owner-before-fields для каждого `cardId`;
- сохранение `CT=99` и маркера ветвления `*`;
- различие отсутствующего и пустого `IV`;
- состав `ISAOBJSINFO` и `FONTSTYLES`;
- UTF-8 BOM и компактный SCADA-диалект;
- self-closing пустых элементов;
- отсутствие пустого `FONTSTYLES`;
- допустимые лексемы Boolean;
- строгий повторный XML-разбор результата.

Поскольку тест перебирает каталог библиотеки, новый шаблон автоматически попадает под общий контракт. При появлении нового `GROBJTYPE`, неразрешённой карточки или нарушения owner-order тест или генерация должны завершиться ошибкой, а не создать предположительный XML. Ожидаемые наборы ID и количества в тестах сейчас рассчитаны на восемь известных шаблонов, поэтому добавление девятого требует осознанно обновить fixtures.

Команда проверки:

```powershell
go test -count=1 ./...
```

## 16. Открытые вопросы и ограничения

1. Успешный ручной импорт подтверждён пока для двух из восьми шаблонов.
2. Точный одиночный триггер прежнего `String → Boolean` не выделен; подтверждена работоспособность полного набора исправлений.
3. Два владельца одного `cardId` пока не считаются отдельной ошибкой — используется первый.
4. Нативный полный порядок независимых блоков не воспроизводится; гарантируется только порядок зависимостей.
5. `cleanNumber` использует fallback для пустых и некорректных числовых параметров; для новых библиотек желательно отдельно проверить отсутствие повреждённых чисел.
6. Нативные файлы содержат байт `0x08` как разделитель `KLPath`, хотя он запрещён XML 1.0. Приложение намеренно не создаёт такой байт и принимает только XML-совместимый путь.
7. `Project`, контроллер, ресурс, `GroupID` и `POUNum` являются контекстом целевого проекта и не выводятся из семантики шаблона.
8. Транспортные ID не гарантированно свободны в произвольной существующей базе.
9. Пересчёт bounding box для `OBJTYPE=7` основан на авторитетности `PL`; отдельного нативного подтверждения для всех полилиний нет.
10. Различающиеся сигнатуры одного типа между legacy-шаблонами не унифицируются автоматически, кроме подтверждённого случая шаблона 19963.
11. Эталонные файлы `AD3 by Scada.xml` и `ADR without input.xml` пока не подключены к тестам как golden fixtures; полное семантическое сопоставление с ними выполнено анализом и ручным импортом.

## 17. Критерии принятия следующего шаблона

Перед признанием нового шаблона поддержанным необходимо:

1. Убедиться, что каждый `grprim` относится к поддерживаемому классу.
2. Проверить разрешимость всех ненулевых `CARDID` через родительский `ISAOBJLIST`.
3. Проверить наличие владельца перед зависимыми полями каждой карточки.
4. Проверить допустимость `COMMENT`, `FP`, `LP`, `PL`, `CI`, `CO`, `VMODE`, `BN` и `CT`.
5. Проверить три состояния `IV` и составные `INITIALVALUE`.
6. Проверить шрифты и наличие пригодного `USERFONT` для отсутствующих стилей.
7. Запустить полный набор тестов.
8. Сгенерировать XML с корректным контекстом целевого проекта.
9. Сопоставить семантику с нативным экспортом, если он доступен.
10. Выполнить контрольный импорт в SCADA и добавить результат в таблицу подтверждённых шаблонов.

До прохождения последнего шага шаблон считается поддержанным реализацией, но не подтверждённым импортом.
